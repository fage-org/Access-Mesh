## 内容定位

本批次文档用于沉淀 AccessMesh 当前阶段的现状核对和结构性问题诊断，回答三类问题：

1. 当前模块边界和事实源分别是什么。
2. 当前最危险的断层和缺口是什么。
3. 下一阶段应该按什么顺序收主线、补能力、做对外交付。

这批文档属于分析与方案收敛记录，不替代 `docs/design/` 下的正式设计文档。涉及正式接口契约、实现约束、表结构时，仍以 `docs/design/` 下对应文档为准。

## 内容去向

## 历史背景

本批次文档形成于一次针对 AccessMesh 全项目的连续核对工作之后。核对范围覆盖：

- Round 1：认证与会话
- Round 2：主体与组织
- Round 3：资源与菜单
- Round 4：授权与权限事实
- Round 5：运行时鉴权
- Round 6：前端权限呈现
- Round 7：补充域、日志审计、类型定义、业务域、example-service 与 SDK 定位

核对过程中已经形成若干关键决策，例如：

- 前端不直连 permission-center，由 admin-service 作为前端唯一后端聚合入口。
- 登录采用最小返回，登录后再拉 userinfo 和 user-menu。
- 业务路由由后端统一下发，前端不再长期维护模板式 mock async-routes。
- 按钮权限最终以稳定 permissions 权限码呈现，现有 auths 模板体系应逐步退场。
- `resource_dependency` 自动补权属于首期必须落地能力。
- example-service 需要在核心主线完成后做成真实接入示例；SDK 需要分 Spring Boot starter、普通 Java SDK、其他语言接口文档三层交付。
