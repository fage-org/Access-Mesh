# 权限依赖自动授权的接入与实现简化评估

本稿承接 [T-PERM-078](../../tasks/T-PERM-078.md)。它是候选比较，不取代 [已采纳设计](../../design/dependency-auto-grant.md)，不表示 T-PERM-071～073 已交付，也不解除 T-PERM-054 的启动门禁。方案取舍随实施决定，再同步权威设计、契约总册与原任务验收。

## 1. 判断与当前事实

推荐保留“业务服务声明关系、写入时计算自动权限、鉴权消费普通授权行”的架构，简化接入编排与推导来源存储。没有证据支持为了这一功能重做整个鉴权引擎。

主要负担不是 JSON 格式，而是用户需要理解不同授权语义、接入程序要协调资源与依赖的生命周期，以及平台计划持久化远多于最终权限结果的推导路径。

当前基线：服务认证前置 T-PERM-070 已完成；071 声明层、072 物化、073 观测仍为 proposed。代码中的 `DependencyAppServiceImpl.rejectAutoGrantTrue` 仍拒绝 `autoGrant=true`（20048）；新编译器、物化器和 registration starter 尚未实现。以下算法风险是设计落地风险，不是当前已启用自动授权的生产故障。

## 2. 先区分用户想省掉哪一种工作

| 需求 | 具体行为 | 合适的机制与边界 |
|---|---|---|
| 授业务权限后，不想再授一次 API 权限 | 授 `REPORT:VIEW` 后对应查看接口可通过入口校验，服务仍校验具体报表实例 | T-PERM-054 的操作与 API 映射；与资源依赖不同，仍待方案定案，不能靠 AUTO_DEP 授 API 绕过 |
| 授 A 时，希望同时获得 B 的独立权限 | 授 `sales-monthly:VIEW` 后获得 `sales-template:VIEW`，以后直接访问模板也允许 | 当前 AUTO_DEP 的合适场景；目标权限条件继承来源，撤销时重算 |
| 只允许在操作 A 时使用 B | 看报表 A 时可以使用数据集 X，不能因此直接浏览或导出 X | 现役 `depend_on` 子权限及主资源上下文是相关基础，但仅支持其现有一层/属性限制，不等于自动多级依赖图；业务调用链还须绑定真实父上下文 |
| 一次给一组稳定权限 | 给“报表使用者”配置固定操作集合 | 可复用预配置角色；批量勾选本身不具备依赖变更、撤销共享来源时的自动回收能力 |

例子取自现设计 §4.1 的 `REPORT/sales-monthly → REPORT/sales-template`，以及契约总册 §6.1 的 REPORT 父上下文与 DATA 子资源示例。当前 AUTO_DEP 明确 `depend_on=NULL`，目标行会被普通鉴权查询直接消费，因此不能把它宣传成“只能在源业务场景中使用目标”。

**产品建议**：先根据实际调用链选择上述语义。操作与 API 映射优先解决常见接入重复配置；资源间自动授予只面向确实接受独立目标权限的业务关系。两者可共用接入向导，但不能合成一张通用依赖图。API 路由准入也不能替代资源实例判定。

## 3. 现方案的复杂点与实际后果

### 3.1 接入入口描述尚未闭合

已采纳设计 §4.1 的 JSON 和 `PermissionManifestProvider.dependencies()` 只产出依赖，§4.3 却承诺 starter 先同步资源。现役 `ResourceEntityFullSyncReq` 必须按类型 scope 提交资源 items，每项还有来源标识和 `SyncVersionRef(occurredAt, sequenceNo)`；它没有 manifest 的 `revision` 字段。因此“两个请求携带同一 git revision”不能直接落到现协议。

动态场景还需要回答：业务新增或删除报表时谁触发同步、如何证明扫描完整、多实例谁负责发布、旧进程重试会不会覆盖新清单。仅提供启动时 Provider 无法完成持续更新。`payload_hash` 能识别内容不同，但不能判断哪个内容更新；git revision 字符串同样不是天然可比较的业务版本。

资源 full-sync 的 `items` 目前带 `@NotEmpty`。资源集合从一条变为零条时，提交 `[]` 被校验拒绝，不能仅凭 FULL 差异语义承诺最后一条资源可回收。失败、超时、分页未读完也绝不能转换为空清单。

### 3.2 常用授权方式与自动补全边界不一致

现设计 §6.1 仅以角色的 MANUAL 实例主授权为种子；类型级 `scope_all`、AUTHORITY_ROOT 和由父实例继承的子资源权限不展开。这是已采纳范围，不作为实现缺陷重报。

实际体验是：某角色获得“所有报表可看”，但不会自动获得每张报表依赖的模板；逐张显式授予才参与补全。若管理员最常使用类型级授权，功能收益会明显受限。实施前用真实角色授权方式判断：保留范围并在授权页明确提示，还是扩展覆盖。后者必须承担资源新增、父关系变化等额外触发面，不能只改种子查询。

### 3.3 全路径存储放大了写入与恢复成本

§3.5 的 support 键包含 `parent_support_id` 与 `source_grant_id`，§6.4 要求逐种子逐路径记录，并用额外遍历补齐窄路径与被压制节点。即使只有少量资源，分叉重汇也可以形成大量路径。

此外，§3.5 要求 support 的 `auto_permission_id NOT NULL` 指向自动授权行，但 §6.3 允许被显式授权覆盖的中间节点没有自动行。§6.4 的“被压制节点挂推导节点”没有对应持久化载体。例如 `A→B→C` 且 B 已被 MANUAL 覆盖，A→B 的中间 support 无可指向的 B 自动行。保留全路径模型必须补齐该表示；改为按需逻辑推导可以消除此存储问题。

### 3.4 管理员 override 不是普通的编辑便利

§5.4 的 ADMIN_UI 声明豁免同 owner 校验，门禁维持 `DEPENDENCY:CREATE/UPDATE/DELETE`；现役依赖写入口不校验目标 `canGrant`，而直接授权另有 ROLE 管理与转授权校验。因此“依赖编辑者的权能不超过直接授权”目前没有依据。

当自动物化启用后，依赖编辑者改变目标，就会改变所有持有源权限的角色的派生权限。当前未发生这种自动扩权，是因为 20048 尚阻止自动授权启用。推荐普通管理员只看来源和结果；跨 owner/平台内部目标 override 暂不进入常规入口。若保留，必须把它明确建模为高信任策略管理能力，或设计目标委托权的持续校验，不能只加一条红色提示。

<a id="alternatives"></a>
## 4. 方案比较

| 候选 | 接入与使用收益 | 主要成本 | 判断 |
|---|---|---|---|
| 原方案完整实现，只改善表单/JSON | 接口语义变动少 | 双清单、完整路径持久化、override 与边界解释仍在 | 不优先；主要成本没有减少 |
| 统一接入入口 + 保留写时物化 + 按需解释来源 | 开发者从同一份业务目录产出同步输入；管理员只维护显式授权；去掉全路径持久状态 | explain 请求需要重新推导；须保证同一已提交视图和结果对比 | **推荐候选** |
| 鉴权时沿依赖关系求值 | 避免按角色物化，动态关系更直接 | 单查/批查/范围查询/Gateway 快照、条件与互斥都要统一改造；撤销与缓存语义重做 | 仅在真实规模与动态场景证明写时方案不合适时再选 |
| 只做权限包或批量授权 | 静态场景最容易使用 | 不会因依赖变化自动更新，也没有多来源撤销语义 | 适用于固定权限集合，不能等价替代自动授权 |

不建议新建 DSL、注解扫描、通用工作流、自动 resolver 或持久队列来完成当前简化；JSON、现有同步领域服务和凭证能力足以作为基础。

<a id="recommended"></a>
## 5. 推荐候选的具体形态

### 5.1 接入方：一个业务目录入口，底层继续复用现有接口

接入方一次描述完整资源集合及其依赖；starter 从同一个已完成读取的快照分别生成资源同步与依赖请求。资源类型、操作与 SYNC 所有权仍由授权管理流程预先定义，不让服务凭证自动取得类型创建或角色授权权能。

这是**SDK 输入模型统一**，并非直接把 `resources` 字段发给现有 manifest DTO。若采用，该模型将不再坚持“配置文件等于 manifest 线格式”，需要明确修改原定案；非 Java 调用方仍可直接使用两个正式同步接口，给出同样的编排示例。

建议工作流：

1. 平台管理员登记服务、类型及操作，签发已有服务凭证；接入页汇总检查结果与缺失前置项。
2. 业务应用提供静态目录，或从业务库构建完整快照；starter 完成默认值、业务键格式、重复键、自依赖、空操作码与清单内显式环的本地检查。类型/操作存在性、所有权与完整已提交图的环由服务端权威校验，不为预检查再建一套元数据缓存。
3. 资源按现有 scope 分组同步；检查业务信封及逐项结果，不以 HTTP 200 认定成功。失败或部分成功有明确诊断，未满足前置资源时不继续发布依赖。
4. 同一份快照中的依赖再发布；第二步失败重试原快照，而不是重新扫描后拼接两次不同结果。重试不得让旧发布覆盖新发布。
5. 业务关系变更后，由明确的发布调用方触发刷新。静态目录可随发布启动；动态目录必须接入业务变更或可验证的周期刷新，启动一次不算动态同步已完成。

复用 T-PERM-070 已有认证配置与头注入，不再建立第二套 credential 生命周期。资源项版本和 manifest 内容标识各守自己的协议，starter 负责关联一次发布、错误定位和重试；具体版本映射、单发布者约束或服务端新旧发布判定，实施前选择最小可行形态。

例如新副本发布 `{A,B}` 后，旧副本迟到提交 `{A}`，每项版本检查并不能保护 FULL 的“缺失即删除”阶段。不能让 SDK 用本机 `now()` 自动把旧目录包装成最新版本；应先明确业务版本来源与同 scope 的发布者约束。配置也须对齐已实现的 `perm.credential-id/credential-secret/allow-insecure`，而不是直接照抄旧 registration 示例再维护一套密钥。

空的完整快照与读取失败必须可区分。最后一条资源删除可选“受 scope 约束的显式空 FULL”或“明确 DELETE 编排”；现役 `@NotEmpty` 未变更前，不宣传前者已可用。不把资源与依赖合为新的跨能力大事务，仅靠统一 SDK 也不能声称两接口原子生效。

### 5.2 平台内部：存结果，按需解释推导

保留 declaration 与 compiled 图的分层：前者保存业务键和失败诊断，后者复用已解析资源与操作关系。先不为减少一张表把两种职责混在一起。

候选计算模型：

```text
同一事务内读取角色显式种子与已提交依赖图
    → 纯推导函数：按 (资源, canonical操作, 条件) 去重，获得逻辑闭包
    → 与现有引擎兼容的压制/操作压缩，得到 desired AUTO_DEP
    → desired 与 actual 做差异更新
    → 提交后按既有机制失效缓存
```

撤销正确性来自当前种子与依赖图的完整重算：A 和 D 都能派生 X 时，撤销 A 后 X 仍在 desired；撤销所有来源后 X 不在 desired。无需以“持久 support 引用计数归零”作真相来源。对账也调用同一推导函数比较 desired 与 actual，不再独立维护全路径资料。

解释入口只回答“为什么生成这条角色自动授权”，不是恢复已经删除的完整用户权限排查功能。它从一致性读视图中的种子与图构建共享推导 DAG，节点为逻辑事实、边为直接推导，按需展开到显式来源。中间节点即使没有物理 AUTO_DEP 行也能表示；多个来源、窄条件被宽条件覆盖的原因都能展示。展开输出可分页/截断并明确标识，不能用展示上限截断真实授权计算。

解释必须区分“按当前事实应生成什么”与“实际存了什么”。发现不一致就报告漂移；不能把推导结果冒充实际权限判定。它不证明用户当前角色有效、条件成立、互斥通过或缓存已刷新。历史变更依旧靠审计；若产品必须保存每次授权的完整历史推导证据，则本候选不能直接替代该需求，应另评估保存范围。

**保留必要机制**：事务、受影响角色定位、同步撤权、INLINE 引用回收、只读 AUTO_DEP、`canGrant=false`、完整写入口与锁序均不能随 support 表一起删除。现设计 apply 只取角色锁、编译先反查角色再取锁，尚需覆盖“新增种子未提交，编译删除边时未发现该角色”的交错；按需 explain 和后台对账均不能代替这条写入一致性约束。可比较共享编译串行边界与版本校验重试，不在本稿擅定实现。

### 5.3 不把更少行数等同于更简单的正确算法

条件传播只允许同一资源、同一被证明操作之间比较宽窄。`A:VIEW` 无条件与 `A:EXPORT` 条件 C 并存，只有 EXPORT 触发 B 时，B 必须带 C；不能被 VIEW 的无条件组吸收。不同非空条件按 OR 保留，不能任取一个或改为无条件。

可以在逻辑推导阶段保留完整条件变体，避免为解释再枚举全部路径；最终物化仍需通过同一规范化函数。**本稿不推荐直接删除显式压制或反链压缩**：当前 `PermissionConflictDomainServiceImpl.computeMutexContext` 按授权行 canonical 位识别互斥操作，并未把 `inheritMask` 展开为相同集合。UPDATE 覆盖 VIEW 时，存 UPDATE 一行与同时存 VIEW、UPDATE 两行，可能对 VIEW 与 EXPORT 的互斥规则产生不同结果。需要按真实引擎做差分验证后才能决定减去这些优化，不能拿纯 OR 布尔模型证明全系统等价。

保留也不等于照搬原算法。现 `OperationPermissionUtils.covers` 仅检查目标 canonical 位，不能据此假设覆盖关系是偏序：自定义操作 X 覆盖 Y、Y 覆盖 Z、X 不覆盖 Z，在现有 `inheritMask` 中可表达。删除 Y 行会丢掉其对 Z 的覆盖；相互覆盖还需要确定性保留规则。规范化应证明保留行覆盖被删除行的全部有效位、条件不更窄，并核对互斥判定/审计；若不能证明，就保留原事实并重新明确互斥语义。这是采用简化候选前必须收敛的设计项，不把原反链视为已验证正确。

### 5.4 管理员：只管理显式意图，自动结果就地可见

授权页建议显示“你授予的权限”与“自动带出的权限”，自动项只读；保存前预览来源、条件、可能新增的独立访问权和撤销后仍会保留的权限。来源入口直接回到可操作的显式授权，不要求用户去依赖图页理解 declaration、compiled、support。

依赖页作为开发/运维诊断：显示服务、同步状态、失败原因与影响角色，内部 revision、编译来源等放详情。普通管理员不编辑服务维护的边；同 owner 手工边、跨 owner override 是否保留另行决定。仍保持类型级/父继承不触发时，授权页必须直接提示边界，不能保存成功后让用户自行排查缺权。

<a id="evidence"></a>
## 6. 小型图验证与证据边界

构造连续菱形 DAG：每一层从前节点分到两个节点，再合到一个节点；每边同操作、无条件，单个显式种子。深度 n 时节点为 `3n+1`，边为 `4n`，最后节点的路径数为 `2^n`。按现设计“每种子×每路径”记录每跳，support 行为 `4×(2^n−1)`；共享逻辑事实和直接推导边仍分别为 `3n`、`4n`。

| 菱形深度 | 资源节点 | 依赖边 | 逐路径每跳 support | 派生逻辑事实 / 直接推导边 |
|---|---:|---:|---:|---:|
| 5 | 16 | 20 | 124 | 15 / 20 |
| 10 | 31 | 40 | 4,092 | 30 / 40 |
| 20 | 61 | 80 | 4,194,300 | 60 / 80 |

2026-09-20 独立 Python 模型验证上述递推，并验证：不同操作的无条件不传播到条件操作、共享目标撤销单源仍保留、撤销宽来源恢复窄条件、多非空条件 OR、被更窄 UPDATE 覆盖的无条件 VIEW 仍保留。实验材料在仓库外 `D:/codespace/Access-Mesh-review-20260920-1148949/auto-grant-model.py` 与同名 JSON；公式和构造在本节即可复算。

这证明可表达的图形存在路径爆炸，也为共享推导提供可行性证据；**不是实际业务规模预测、数据库压测或引擎等价证明**。它未验证 SQL、并发、互斥、鉴权快照与线上延迟。取消 support 仍需在真实实现中验证同一事务撤销和解释一致性。

## 7. 实施前决策与现任务衔接

| 待决定事项 | 推荐倾向 | 行为差异与验收依据 |
|---|---|---|
| 真实首个业务场景 | 先确认独立目标授权确实可接受 | 用现设计月报/模板走查；若要求仅父上下文内读取数据，不把普通 AUTO_DEP 当等价实现 |
| SDK 目录入口与发布生命周期 | 同一完整快照产资源和依赖，复用原接口 | 验证多类型资源、部分失败、最后一条删除、旧发布迟到、进程重启重试、动态关系变化；不以“一个方法”掩盖版本协议 |
| 来源证明持久化（U009） | 按需共享推导，去掉逐路径持久 support | 验证菱形图、共享来源撤销、被压制中间节点、窄来源恢复与 explain 的 actual/desired 区分；历史证据需求明确后才能最终决定 |
| ADMIN_UI override | 常规入口先不提供跨 owner/内部目标越界建边 | 保留则明确信任边界与持续授权策略；MANIFEST 行管理面只读护栏仍保留 |
| scope_all / 父继承覆盖 | 不默认扩展；先验证常用角色模型是否接受 | 保留则直接提示；扩展则补资源新增/移动触发与写放大验证，不能仅改种子 |
| 压制/反链及条件规范化 | 保留独立规范化步骤，先证明语义再决定压缩规则 | 用非传递覆盖、相互覆盖、条件与互斥的适用反例差分；不同操作的无条件吸收必须修正 |
| 编译与新增授权并发 | 主事务内证明一致性 | 授权读旧图、编译删边未发现新角色的交错必须被阻断或重试，不能等待后台对账补救 |
