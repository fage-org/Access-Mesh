> 状态：done（2026-09-19 收口）
## 背景

外评发现（2026-09-19 立项，frontend-session-consistency 计划）：用户页成员 Tab 的删除操作（MemberTab 直渲按钮与「更多」dropdown 两入口）点击即删、无任何确认——一次误点即销毁一个用户账号；且 `useUserManage.handleDelete` 无 catch，删除失败（后端业务拒绝如 CANNOT_DELETE_SELF 删除自己、实例级权限拒绝、网络异常）时 rejection 无人处理，用户零感知，列表不刷新也无提示。对照同页族先例：停用/重置密码（MemberTab）与组织删除（ReOrgTreePanel.onDelete）均已有 ElMessageBox.confirm，角色删除（role/utils/hook.ts handleDelete）确认+错误反馈齐全——用户删除是同页族唯一裸奔的销毁性操作。

## 范围

- `src/views/system/user/utils/hook.ts` `handleDelete`：加确认弹窗（取消 return）+ 删除路径 catch 错误反馈（照角色页 hook 先例形态）。
- 新增 `src/views/system/user/utils/hook.spec.ts`：3 条 old-fail 回归锁。
- MemberTab 无需改动（两入口均走 hook 的 handleDelete）。

## 边界（与 T-FE-051 分工）

- 本卡只做**删除路径**的确认与错误反馈；`loadTable` 失败提示与 `handleCreate/handleUpdate` 的 catch+message 一致性收口归 T-FE-051（其卡 acceptance「外评 #3 错误反馈面与 T-FE-047 确认弹窗互补」）。
- 错误文案来源统一（非 2xx 消费后端 body message）归 T-FE-051；本卡沿用 `error.message || "删除失败"` 既有先例形态。

## 当前口径

- 确认文案：`确认删除用户 "<name>"？删除后该用户将无法登录，所属组织与岗位关联将一并移除。`（后果句对齐后端真实级联：解绑 user_org/POSITION 投影 + 软删用户 + 删 abstract_user 投影）。
- 取消 = 用户明确反悔，静默返回（角色页同款两段 try/catch：第一段管确认、第二段管删除）。

## 验收对照

见 frontmatter acceptance。

## 非目标 / 遗留

- 组织删除确认——ReOrgTreePanel.onDelete 已有，无缺口。
- 批量删除 UI——当前无该入口，后端 IdsReq 虽支持批量但前端单行删除，不新增入口。
- 删除后勾选态/分页越界等列表维护——当前无多选删除场景，不做。

## 完成记录（2026-09-19）

- `user/utils/hook.ts handleDelete`：照角色页 hook 先例改两段 try/catch——第一段 `ElMessageBox.confirm`（取消即 return，零请求零提示）；第二段 `deleteUser` + 成功提示 + `loadTable()` 刷新，catch `message(error.message || "删除失败", { type: "error" })`。确认文案含用户名与真实后果（无法登录 + 组织/岗位关联一并移除，对齐后端 UserWriteAppServiceImpl.deleteUser 级联语义）；后端业务错（如 CANNOT_DELETE_SELF）经 RequestError.message 透出。MemberTab 两入口（直渲按钮 + dropdown command）经 hook 自动全覆盖，组件零改动。
- 回归锁 3 个（新增 `user/utils/hook.spec.ts`，照 biz-domain hook.spec mock 范式）：确认后才发删除请求（含确认文案用户名/后果断言）、取消零请求零提示不刷新、删除失败透出后端 message 且不刷新。红跑实证：stash hook.ts 复跑 **3 用例全红**，恢复后全绿。
- 验证：全量 vitest 242/242（16 文件，+3 新用例）、typecheck、lint（exit 0，本次无格式回流裹挟）、build（22s，3.43MB）全绿。
