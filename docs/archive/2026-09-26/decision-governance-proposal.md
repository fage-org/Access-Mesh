# 方案 B：当前规范归位、定案入口轻量化、历史按需追溯

**核心设计：不再维护一份“每次评审都要读的全仓定案副本”。持续有效的决定直接进入所属权威规范，登记表只负责定位，历史记录只在需要解释、核对或追溯时读取。**

本方案以 `feat-permission-center` 的 `c0604ad4` 为基线，当前最新提交仍是 T-ACCESS-063 双册治理。以下是待实施的治理方案，不改变既有业务决定，也不把“已采纳方案”视为“已经实现”。

---

## 一、目标、边界与核心约束

### 1. 最终要解决什么

本方案需要同时实现四个目标：

| 目标 | 具体要求 |
|---|---|
| 决定不丢失 | 用户拍板当轮有仓库载体，后续会话能追溯 |
| 当前口径明确 | 不需要通读历史，才能拼出现在应该遵守什么 |
| 日常读取成本可控 | 无关任务、历史修复和评审轮次，不增加本次任务的必读内容 |
| 既不重复提问，也不掩盖问题 | 相同前提下不重复推翻决定；新回归、范围外问题和前提变化仍可报告 |

**这里的“永久解决”不是让文档永远不增长，而是让历史增长不再自动转化为所有任务的阅读负担。**

合理的消费关系应当是：

```text
本次任务所需约束
= 少量通用协议
+ 本次涉及主题的当前规则
+ 相关有效例外
+ 必要时追溯的历史证据
```

不能再是：

```text
本次任务所需约束
= 全仓仍保留在现行册中的全部定案
```

### 2. 本次明确替换的旧机制

现有协议要求定案逐次追加、常青行永留、评审整读现行册，并使用两档评审处置。本方案需要显式替换其中的消费与存储职责，不能只在原机制上继续补规则。

| 现有机制 | 方案 B |
|---|---|
| 每次拍板都向现行册追加一行 | 当轮写入对应权威载体，不必增加入口条目 |
| 常青行永留现行册 | 长期约束留在所属规范，不保留第二份定案正文 |
| 每次评审整读现行册 | 读取小入口，再加载相关主题与例外 |
| 被取代内容与现行条目并存，由读者还原 | 当前规范直接表达当前口径，历史保留演进过程 |
| “以前已修”“接受现状”混合成勿再报 | 修复证据与有效接受边界分开处理 |
| 定案口径统一硬限 200 字 | 入口保持短小；正文按语义完整性控制，不截掉前提和边界 |

### 3. 不引入什么

不新增决策数据库、向量检索、自动索引服务、独立 ADR 文件体系、全仓例外总表或新的全局决策编号。

也不要求为了这次治理重写所有设计文档。**已有合适章节就直接归位；只有缺少真实承载位置时，才新增相关章节。**

## 二、文件职责：入口、当前规范、执行状态、历史各归其位

### 1. 权威职责分配

| 载体 | 新职责 | 不应承载的内容 |
|---|---|---|
| `AGENTS.md` | 少量跨任务硬约束，以及规范和定案入口指针 | 定案时间线、任务进展、不断扩充的“勿再报”清单 |
| `docs/design/decision-registry.md` | **定案导航入口**：简短使用提示、主题路由、历史入口 | 每条决定的摘要索引、决定正文、评审处置历史 |
| `project-rules.md` 的文档治理章节 | 定案归位、修改、追溯与评审适用性的统一治理规则 | 各业务领域的具体决定 |
| 现有设计、契约、Rules、Skills | 按既有权威划分承载当前规则、必要理由和有效边界 | 按日期追加的讨论与评审流水 |
| 任务卡 | 当前执行范围、验收、任务级安排、完成证据；引用相关设计 | 另一份完整业务契约、逐轮决策日记 |
| `pending-problems.md` | 尚未具备实施条件的问题及其状态，关联决定与任务 | 复制设计结论、维护另一套豁免正文 |
| Git 历史与 `docs/archive/` | 原始决定、被取代内容、讨论过程与历史证据 | 默认作为当前实现依据 |

这里复用现有分层，不另造体系。仓库已经要求设计承载长期决定、任务不能重新定义契约、任务完成前回写设计；任务卡也已限定为当前口径和终态证据，而不是评审流水。

### 2. `decision-registry.md` 的终态结构

建议保留文件名，避免没有必要的入口迁移；标题可以改成“定案入口”。

只保留三个部分：

```markdown
# 定案入口

## 使用说明
治理协议位置；当前规则与历史证据的区别；按任务范围读取。

## 主题路由
主题 / 触发场景或关键词 / 权威位置

## 历史追溯
迁移前登记表、历史册的位置及基线版本。
```

主题路由应当按**稳定的业务或工程主题**组织，例如：

| 主题 | 典型触发条件 | 指向的已有权威载体 |
|---|---|---|
| 通用工程约束 | 响应结构、命名、分层、时间、数据校验 | `project-rules.md` 对应章节 |
| 权限查询与互斥 | 引擎、角色判定、权限集合、范围权限 | 权限编码规则、`engine/` 对应文档 |
| 自动授权与资源依赖 | 依赖发布、推导、撤权、对账 | `dependency-auto-grant.md` |
| 接口认证与准入 | 服务凭证、接口门禁、授权入口 | API 契约、服务认证设计及相关实施设计 |
| 组织与用户生命周期 | 默认树、成员、岗位、组织可见性 | 对应组织与用户设计 |
| 前端会话与菜单 | 登录、菜单刷新、路由准入、权限恢复 | 对应前端设计 |
| 文档与评审工作流 | 定案、任务收口、外评、归档 | 文档治理章节、相关 Skills |

这是路由组织方式，实际落位时应补充准确章节锚点。

**不能给每个决定增加一行路由。** 同一主题产生十次新决定，通常只更新该主题的正文，不增加十个入口条目。

入口也不重复 `AGENTS.md` 或设计索引的整张权威表。已有明确入口的主题，直接复用其定位方式。

### 3. 防止把大登记表搬进另一个大文件

规范归位不是把全部定案追加到 `project-rules.md` 末尾。

具体要求是：

**已有规则覆盖的内容，直接合并进原规则；主题专属内容归主题文档；例外紧邻被它限定的规则；历史解释只保留必要指针。**

例如分页信封规则已经有所属章节，就在原章节表达当前形态，不再加一个“分页相关历次定案”附录。

同理，读取时应定位到相关章节，而不是因为命中一个主题，就强制阅读整本 API 契约或所有引擎文档。

## 三、内容模型：区分规则、例外、安排与证据

本方案不增加复杂的数据结构，但要求写入前先区分内容性质。

### 1. 五类内容及其落点

| 内容类型 | 判断标准 | 落点与处理方式 |
|---|---|---|
| 当前规则 | 后续同类实现持续需要遵守 | 写入所属规范，表达当前结论及必要边界 |
| 有效例外 | 在特定范围或前提下，接受与通常要求不同的行为 | 写在所属规则附近，明确范围、代价与复核触发条件 |
| 任务级安排 | 只约束某项任务或迁移阶段 | 留任务卡；跨任务的安排由相关任务互相引用 |
| 修复与验证事实 | 描述某问题如何修复、哪些证据已取得 | 当前代码与测试、任务完成证据、提交记录 |
| 历史决定 | 已被取代，或者只用于解释为什么这样设计 | 历史版本或归档，不进入默认消费面 |

特别需要区分：

> **“永久选择不采用某机制”通常是当前设计规则，不是永久挂着的临时例外。**  
> **“本次暂不解决某问题”才可能需要一个仍有效的接受边界。**

“发现了问题，但尚未决定如何处理”则仍属于问题清单，不能写成已接受风险。

### 2. 当前规则的最小表达

普通规则直接用自然语言写入原章节，不要求每条都套模板。只有容易引起重复争论的决定，才补齐以下信息：

```text
结论：现在采用什么。
范围与边界：适用于哪里，不适用于哪里。
必要理由：为什么选择它，接受了什么代价。
来源：明确的任务、原定案或已保留提交。
```

其中，“必要理由”不是要求保留所有候选方案，只需保留未来容易被错误推翻的关键原因。

例如某方案是因为没有实际消费者而暂不实现，应保留这个前提；不能压缩成无条件“禁止实现”。

**原记录没有说明理由时，不得在迁移中补造用户动机。** 可以保留结论与来源，注明依据中没有记录理由。

### 3. 有效例外的最小表达

例外应比普通规则更严格，因为它会影响评审是否上报问题。

建议至少包含：

```text
适用范围：具体路径、行为、阶段或场景。
接受内容：允许什么偏离，接受的影响是什么。
决策依据：谁在何时确认，仓库依据在哪里。
复核触发：哪些事实变化后，需要重新核实其适用性。
```

这里的“谁确认”应依据现有记录表达，例如“用户于某日拍板，见某任务记录”，不能把代理自行推导写成用户决定。

**不要求每个例外都设置日历到期时间。** 更适合本项目的是事件触发，例如相关替代实现交付、原路径删除、实际消费者出现、影响范围扩大。

复核触发也不是自动翻案：

> 关联任务标记 `done`，只能触发核实；是否解除例外，要看它承诺的替代行为是否真正落实。

### 4. 不新增“全仓有效例外表”

有效例外应放在它约束的主题附近，而不是从大登记表再拆出一张大豁免表。

同一个例外涉及多个主题时，选择一个明确的归属位置，其他章节只链接，不复制完整正文。

如果某条内容只约束任务验收安排，例如“本卡全量回归合并到后续基线任务执行”，就留在任务卡和相关验收引用里，不必升格成全仓规范。

### 5. 定案身份与引用方式

不新增 `DEC-001` 一类全局编号体系。

需要跨文件引用的重要决定，使用**稳定的主题锚点**；普通规则无需逐条编号。来源则复用任务 ID、原定案位置或已保留的提交版本。

应区分两种链接：

| 链接用途 | 应指向哪里 |
|---|---|
| 当前实施依据 | 当前有效规范及稳定章节 |
| 历史证明 | 当时的任务记录、归档或具体版本中的原文 |

历史原文可以通过 `commit:path` 定位；Git 支持读取指定提交中的文件内容。作为唯一证据的提交必须能够持续取得，不能只存在于临时本地分支；合并改写历史时，应保留必要证据或更新来源。:chatgpt-content-reference{index="4"}

## 四、生命周期与写入协议

### 1. 首次形成决定

保留“用户定案当轮落仓”的要求，但将其改为：

> **当轮确定权威落点并记录结论，不再要求当轮向总表追加一行。**

处理过程如下：

**先判定决定的适用范围，再更新对应载体，最后补来源和必要引用。**

长期规则更新所属规范；任务安排写任务卡；接受暂时边界时更新所属主题的例外说明，并关联已有任务或问题。

已有实施任务的事项不再重复创建问题条目。尚不足以实施的问题继续使用现有 `pending-problems.md`，但其中的“拍板后移 registry”需要改成“拍板后写入所属权威载体并建立引用”。当前问题模板确实仍使用了移入 registry 的表述，需要同步修改。

### 2. 同一决定发生修订

当前规范直接更新成新的有效结论，不能继续堆积：

```text
9 月 1 日采用 A
9 月 8 日补充 B
9 月 15 日否决 A 的一部分
9 月 20 日改为 C
```

当前正文应表达“现在采用 C，以及仍然有效的 B 边界”。

旧版本留在历史证据中；发生实质性替代时，在变更依据中说明替代范围。

**不允许仅凭更新时间更晚，就认定它已经取代旧决定。** 必须有明确采纳依据和适用范围。

### 3. 部分取代

迁移和后续修改都以**独立语义**为单位，不以 Markdown 表的一整行为单位。

旧条目有三个决定，其中一个被取代，就分别处理三个决定。不能因为共享一行，而把已经失效的部分继续当作现行约束；也不能把仍有效的部分一起移除。

### 4. “已定案”与“已实现”分开

这是权限引擎迁移期间必须保留的区分。

现有设计生命周期将 `adopted` 作为权威设计，但它本身不是代码交付证明。方案 B 不需要新增一套文档状态，只需在存在迁移差异的章节明确：

| 信息 | 回答的问题 |
|---|---|
| 已采纳目标 | 最终应该实现什么 |
| 当前实现 | 当前代码实际处于什么状态 |
| 迁移期安排 | 哪些差异已被允许，适用至什么阶段 |

现有登记已经记录了 T-PERM-082 新旧引擎并行、暂不注册新类、具体能力由后续任务承接等边界。这类内容应归入 R2 设计中的迁移说明，而不是通过整读登记表才能找到。

设计采纳不等于实现完成；反过来，代码已经存在也不等于其行为已经获得设计授权。

### 5. 任务完成或归档

任务完成不能自动导致决定失效，也不能自动证明例外解除。

任务收口时应核实：

**长期结论是否已经归位；任务级安排是否完成；相关有效例外是否仍有必要；当前引用是否能够解析。**

归档任务卡后，当前规范继续保留有效规则。历史任务只负责证明当时的选择和执行过程。

这延续仓库既有的“done 前回写设计”，但将检查重点明确为**有效约束是否有当前承载位置**。

### 6. 多来源冲突

不能规定“登记表永远优先”“代码永远优先”或“最新文件永远优先”。

应分别核对：

- 同一语义是否有明确的新采纳记录。
- 是否属于不同适用范围或不同迁移阶段。
- 是否有被明确授权的局部例外。
- 是否只是文档未同步，或者实现偏离了决定。

明确的局部例外只在其范围内生效；任务卡不能凭一个未经采纳的句子改写全仓规则。

无法消解的真实冲突应保留证据并明确指出，不由代理通过日期排序或自行合并含义“解决”。

## 五、开发与评审的消费协议

### 1. 开始任务前：定位相关约束

仓库现有 `AGENTS.md` 已要求先识别模块与场景、加载命中的规则、读取对应设计，而不是扫描全部文档。方案 B 将定案消费纳入同一流程。

具体采用三个输入的并集：

```text
任务卡的 design_refs
＋ 修改对象及其调用关系涉及的主题
＋ 任务描述中的业务概念和跨领域约束
```

不能只按修改文件目录匹配。修改某个组织服务，也可能触及权限、事务、缓存或前端会话一致性。

默认读取小入口和相关规范章节；只有需要解释历史、核对例外或消解冲突时，才扩大到历史材料。

### 2. 双轨与外评如何调整

**双轨评审不再注入整本 registry。**

两轨共同获得本次评审的基线版本、任务范围、相关规范位置及有效边界；各自仍可根据发现扩展读取，不能被主代理选择的几段摘录限制住。

外评也删除“第一步完整读取现行册”的要求，改为定位并读取本次适用的当前约束。

多通道应使用同一评审对象和同一初始范围，避免把不同版本或不同边界的结论混在一起。

### 3. 候选发现形成后：再核对适用性

开始前按主题加载不能完全替代报告前的核对。

每条候选发现都应对照相关当前规则；涉及“应恢复某能力”“不应该这样设计”“某已知边界应修复”时，还应检索相关决定和历史依据。

建议采用下面的处置规则：

| 候选发现 | 处置方式 |
|---|---|
| 相同范围、相同前提下重复提出已否决方案 | 不重复进入用户决策队列，记录所依据的当前规范 |
| 与有效接受边界完全相同，没有新的影响证据 | 作为已知边界处理，不重新包装为新缺陷 |
| 实现违背当前定案 | 报告实现与定案冲突 |
| 以前修过，但当前证据显示再次出现 | 按回归问题核实，不能凭“已修”撤回 |
| 同一类问题发生在例外范围之外 | 单独评估，不扩大旧豁免 |
| 原前提失效或影响扩大 | 指出变化和旧决定的关系，再评估是否需要调整 |
| 依据不足、来源冲突 | 说明具体未核实项，不直接认定缺陷或直接撤回 |

**“存在历史记录”只说明有线索，不自动构成撤回依据。**

### 4. 历史检索不再依赖“感觉像旧定案”

应明确需要历史核对的场景，而不是只有代理“疑似记得”时才搜索。

重点包括：恢复或删除已有机制、改变既有接口行为、扩大既有范围、要求重新处理已知风险，以及文档之间出现冲突。

检索至少结合相关任务号、业务概念、类或方法、新旧名称。搜索命中后必须阅读足够上下文，确认适用范围和替代关系。

检索还要覆盖 `.claude/` 与 `.agents/` 等指令目录，不能只搜 `docs/`。使用 `rg` 时应注意其隐藏文件过滤，必要时显式使用 `--hidden` 并限定搜索路径。:chatgpt-content-reference{index="9"}

### 5. 可替换现有评审硬性纪律的文本

下面这段可以作为消费协议的核心措辞，细节仍由治理规范统一解释：

> 开始评审前，读取定案入口，并根据任务引用、修改范围及相关业务概念定位当前有效规范与例外。不得默认整读历史登记或全部设计文档。  
> 报告候选问题前，核对相关当前规则；涉及已知取舍、能力恢复、范围调整或历史边界时，追溯原决定及其替代关系。  
> 相同范围和前提下，不重复要求用户作出已经明确的选择。既有修复记录不构成永久豁免；实现回归、范围外问题和前提变化仍应核实。  
> 以当前规范说明应有行为，以代码及验证证据说明实际行为，不把设计采纳当成交付完成。  
> 报告中列出与结论相关的依据；需要撤回有争议的发现时，说明具体匹配的决定与适用范围，不再用“已读 registry 全文”作为完整性证明。

撤回依据保留在本次评审结果中即可，不再追加到全仓禁报清单。

## 六、用现有条目说明归位方式

### 1. T-PERM-083：同一条复评记录拆成不同用途

当前登记把 Javadoc 修正、摘要截断接受、后续任务承接及上一轮修复确认放在同一条记录中。

按方案 B，应分别处理：

| 原内容 | 新落点 |
|---|---|
| Javadoc 的 OR 修正为 AND | 当前接口语义与修复证据，不建立永久禁报项 |
| 单条审计摘要截断暂时接受 | 所属引擎设计的有效边界 |
| 后续由 T-PERM-088 收编 | 边界的关联任务和复核触发 |
| 上一轮集合顺序修复确认 | 任务完成证据或提交历史 |
| T-PERM-083 全量回归合并到 T-PERM-095 | 两个任务之间的验收安排，不升格成全仓规则 |

其中，摘要截断的整理形态可以是：

```text
主题：旧单条 PERM_MUTEX 审计摘要截断

范围：本次定案接受的旧单条通知路径。
决定：沿用现有摘要截断行为；规则明细可能未完整进入摘要。
依据：2026-09-26 T-PERM-083 的用户拍板记录。
关联：T-PERM-088 的证据模型与受控提交改造。
复核触发：替代实现实际落地，或出现超出原接受范围的新影响。
```

这个示例是对现有决定的归位表达，不代表重新核实了相关代码，也不把它扩大为所有审计路径的豁免。

### 2. T-PERM-082：迁移例外紧邻迁移设计

新旧引擎并行、暂时未接入生产消费者、后续任务承接等内容，应写入 R2 设计的迁移章节。旧权限编码规则只保留指向该例外的引用，不能同时复制完整例外。现有登记已明确这些是迁移期授权安排。

这样，评审新引擎时能够找到例外；评审无关的前端功能时，不需要阅读它。

迁移结束后，核实实际状态，再从当前规范移除已结束的过渡说明。原选择仍由历史版本证明。

### 3. 已经被现行规范吸收的长期规则

不再保留“规范正文一份、登记表摘要一份、勿再报措辞一份”。

当前规范保留结论、必要理由与来源；登记入口仅指向主题。后续同类问题直接按规范判断。

这也是方案 B 最主要的减量来源：**消除重复承载，而不是不断压缩措辞。**

## 七、存量迁移与原子切换

### 1. 迁移输入

不能只读取压缩后的现行册。

迁移应核对：

**当前现行册、当前历史册、已推翻部分，以及压缩前版本中的原始边界。**

T-ACCESS-063 采用了迁移性压缩，部分长行没有按 200 字硬卡，其验收包括行数守恒和抽样保真。因此，方案 B 的迁移不能把行数一致直接当作语义完整性的证明。

对被压缩过且含独有决定的内容，需要回查压缩前父提交 `c6270d0…`，确认范围、前提、否决原因和未完成事项没有被误当成叙事删除。

### 2. 历史文件的终态处理

建议采用一次性收口，不长期维持新旧两套登记机制：

| 文件 | 处理 |
|---|---|
| 现有 `decision-registry.md` | 先保留原文快照，再重写为小型入口 |
| 现有 `decision-registry-history.md` | 原文迁入本次治理的归档批次，停止继续充当日常追加册 |
| 现有“已推翻”部分 | 随原文快照保留，参与迁移核对，不继续放在小入口里 |
| 后续新决定 | 直接归入所属规范或任务，历史由版本与必要归档承载 |

归档目录使用实施时的日期，不预设新的任务编号。

旧历史文件中的协议属于历史内容。可以保持其正文不改写，由归档批次说明标明“历史协议，不再约束当前消费”，避免为了修改历史头部破坏原文保存。

活跃文件中的旧路径和旧读取指令必须同步更新；历史快照不要求追随当前路径不断改写。

### 3. 迁移核对单位：有效语义，不是原表行

建议建立一份**一次性的迁移对照证据**：

| 原始位置 | 独立语义 | 分类 | 新落点 | 核对结果 |
|---|---|---|---|---|
| 原文件、版本、条目 | 原条目中的某一个决定 | 当前规则／例外／任务安排／历史 | 文件与章节 | 已保留、已被取代或需继续核实 |

它只用于证明此次迁移完整性，完成后随治理任务归档，不成为新的永久登记表。

特别要检查：

**“本表为正文登记点”的会话决定、部分取代项、暂缓安排，以及历史册中仍可能有效的边界。**

不能因为一条内容在历史册、对应任务已经归档，或者超过某个天数，就直接判断它不再有效。

### 4. 实施顺序

| 阶段 | 主要工作 | 退出条件 |
|---|---|---|
| 第一阶段：固定基线与明确落点 | 保留历史快照，确定治理协议和主题归属 | 每类内容有明确承载规则 |
| 第二阶段：逐项归位 | 合并当前规则、整理有效例外、核实替代关系 | 有效语义均有当前落点，独有决定未丢失 |
| 第三阶段：统一切换 | 重写小入口，修改 AGENTS、Rules、Skills 与关联引用 | 不再存在互相冲突的活跃读取协议 |
| 第四阶段：场景验收 | 验证重复定案识别、新问题上报、追溯与读取成本 | 关键场景通过，迁移证据归档 |

**第二阶段完成前，不能提前停用旧消费协议。**

可以先起草新协议，但让它正式生效时，相关规范归位、入口和消费者修改必须是一个完整批次，避免“旧表不读了，新落点还没齐”的空档。

对于仍不能确定含义或有效性的条目，不得静默丢弃。可能影响当前行为的未决迁移项，应阻止该批切换，先补证据或明确裁决。

### 5. 切换失败时的回退

回退对象是这次治理变更，包括入口、读取协议和配套路由，不涉及业务代码或既有业务决定。

若验收发现遗漏关键约束，应先补齐迁移；确需回退时，整体恢复一致的旧消费方式，不能只恢复某个 Skill，留下另一套协议继续生效。

本次治理应另行立项，保留 T-ACCESS-063 作为已完成的历史阶段，而不是把它改写成“从未完成”。

## 八、实际修改清单与验收标准

### 1. 必须修改的文件面

| 修改面 | 具体改动 |
|---|---|
| `project-rules.md` 文档治理章节 | 增加归位、生命周期、有效例外与历史追溯规则，作为治理单一权威 |
| `decision-registry.md` | 从现行定案正文集合改为小型导航入口 |
| `AGENTS.md` | 删除全文消费含义，保留定位指针与简短工作流程 |
| `external-review` Skill | 删除全文自读和全文已读声明，替换为范围定位与候选发现复核 |
| `dual-track-local-review` Skill | 删除整本注入，调整两轨初始上下文和撤回依据要求 |
| `design-plan-task-lifecycle` Skill | 将“当轮登记 registry”改为“当轮归位”；补收口时有效例外检查 |
| 对应 `.claude/.agents` 副本 | 同批同步，不形成两套消费协议 |
| 相关设计、契约、Rules、Skills | 按主题接收当前结论及有效例外，不追加历史流水 |
| `pending-problems.md` 及其模板 | 替换 registry 正文依赖，保持问题与决定分工 |
| 活跃索引、任务引用、提示词 | 更新受影响路径和旧协议措辞 |
| 归档批次 | 保存原文快照及一次性迁移证据 |

当前 `.claude/rules/docs-governance.md` 本来就是指向 `project-rules.md` 的薄入口，应保持这一形态，不把新协议再复制一遍。

检索用于找出残留，但不能把历史引用、引用旧协议的说明文字自动判为错误。必须区分它是否仍在约束当前工作流。

### 2. 不增加永久治理工具

本方案不依赖新工具落地。

可以在迁移时使用一次性脚本核对原文哈希、文件差异、链接和对照覆盖；**脚本只证明它实际检查的项目，不能代替语义核对。**

不为此新增索引生成器、常驻状态同步器或 CI 规则体系。后续是否自动化，应由实际维护成本和反复发生的问题决定，不在本轮预先建设。

### 3. 内容与流程验收

| 验收场景 | 必须达到的结果 |
|---|---|
| 相同前提下重复提出已否决方案 | 能找到有效决定，不重新请求用户拍板 |
| 某问题历史上已修，当前再次出现 | 仍按当前证据评估，不被历史记录压制 |
| 例外只适用于单条路径，批量路径出现类似问题 | 不扩大豁免范围 |
| 原决定被部分取代 | 默认读到正确的当前组合，不需要读者拼历史 |
| 目标方案已采纳但未实施 | 不写成现状或验收完成 |
| 关联任务标记完成但替代行为未证明 | 不自动解除例外 |
| 决定最初只存在于会话登记 | 能在新体系中找到当前结论和原始依据 |
| 任务卡归档或设计文件迁移 | 当前实施依据仍可定位，历史证据仍可追溯 |
| 双轨及外评使用同一评审对象 | 能获取相同的当前规则版本，并可独立扩展读取 |
| 新增大量无关历史记录 | 不增加该任务的默认必读内容 |

其中，**误撤回真实新问题**与**丢失有效决定**应作为阻断项，不因入口显著变小而放行。

验证可以使用已有历史案例和文本场景复核；本次纯文档治理不以重新运行全仓业务测试证明成功。确实涉及测试或代码变更时，再按对应范围验证。

### 4. 体量与维护成本验收

建议把小入口的体量目标设为**约 4KB**，只作为职责检查的参考，不作为需要截断内容的硬指标。

超过目标时，首先检查是否混入了决定正文、逐条历史索引或任务状态，而不是立即压缩文字。

更重要的验收是：

**同一主题增加新决定，不应要求修改多份完整正文；一次普通修复，不应增加全仓永久禁报项；新增无关历史，不应扩大本次任务的强制上下文。**

对跨领域改造或全仓评审，相关规则本身仍可能很多，应按主题分段核查。方案 B 不承诺这类任务可以只读几 KB，也不通过隐藏必要信息来实现“小上下文”。

## 最终形态

完成后，Access-Mesh 不再依赖一张持续膨胀的时间表告诉代理“所有事情以前是怎么决定的”。

它会形成明确的分工：

**当前规范回答“现在应该怎么做”；有效例外回答“哪些已接受差异仍适用”；任务卡回答“这次做到什么程度”；历史回答“当时为什么这样决定”；定案入口只回答“到哪里找”。**

真正要保持长期稳定的，不是某个文件的大小，而是这五种职责的边界。只要不再把每轮修复、每次评审和每段历史重新加入全仓必读集合，就能从结构上消除这次登记表反复膨胀的主要来源。
