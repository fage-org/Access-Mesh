### [P2] 上传落盘后元数据失败，缺少回滚清理

**位置：** [BootstrapGraphDefinition.java:324](D:/codespace/Access-Mesh/access-service/src/main/java/cn/ac/fage/accessmesh/access/bootstrap/BootstrapGraphDefinition.java:324)；[FileAppServiceImpl.java:292](D:/codespace/Access-Mesh/access-service/src/main/java/cn/ac/fage/accessmesh/access/platform/service/impl/FileAppServiceImpl.java:292) 的 `uploadFile`（落盘在 309 行，数据库插入在 331 行）；[access-service.sql:444](D:/codespace/Access-Mesh/docs/design/schema/access-service.sql:444)。

**问题：** 文件先写入持久卷，再插入 `sys_file`。插入或事务提交失败时，数据库回滚，但没有清理本次物理文件的补偿路径。此顺序是存量实现；本次新增标准上传路由及可委派 CREATE 权限，使其进入正常租户使用路径。

**触发条件：** 有目标分类 CREATE 权限的用户上传大小、扩展名合规的 `.txt`，文件部分的 Content-Type 使用 `application/` 加 120 个 `x`，共 132 个字符。服务对未知 MIME 仅记录警告，随后落盘；但 `file_type` 是 `VARCHAR(128)`，插入必然失败。这不依赖数据库故障。

**影响：** 请求失败却留下没有元数据的文件，列表和删除 API 均无法定位它。每次重试生成新的 UUID 文件，持续占用持久卷。

**证据：** 292–296 行不拒绝该 MIME，309 行完成落盘，326 行原样赋值，331 行才插入；上传路径没有回滚清理。已核对 MyBatis 3.5.19 的 `StringTypeHandler` 源码，其使用 `setString` 绑定原值；PostgreSQL 对超长、非空格的 varchar 插入明确报错。[PostgreSQL 16 官方说明](https://www.postgresql.org/docs/16/datatype-character.html)。

已按文档治理复核 [文件契约 §17.1.5](D:/codespace/Access-Mesh/docs/design/access-service-api-contract.md:2253) 及 T-ADMIN-023：已接受的是**删除提交后清理失败保留孤儿文件**，不覆盖这里的上传回滚。上述触发链依据代码、DDL 和官方语义确认，本轮未执行复现测试。

**建议：** 在现有文件服务中统一补上事务回滚补偿，仅清理本次生成的路径，复用已有物理清理逻辑；可持久化字段的长度检查前置到落盘之前。补一条真实 PG 反例，断言元数据失败时物理文件也被清理，无需新增回收平台。
