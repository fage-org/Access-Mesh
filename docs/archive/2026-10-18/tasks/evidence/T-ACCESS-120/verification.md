## 结论核实与处置

外部结论为 P0=0、P1=0、P2=1、P3=0，过度设计候选为零。P2 是取锁同步等待中断后，底层命令迟到成功并续期，而调用方已经退出且没有释放责任。报告另列既有 TreeWriteLockSupport 同族观察。

主代理对照本机 Redisson 4.8.0 JAR 字节码与真实 Redis 反例核实：不能从同步等待退出推导底层命令已取消；普通解锁异步失败的结果处理会取消续期，因此不把“catch 解锁异常”单独认定为永久锁。已接受的 Redis 续期丢失和提交后密码交付窗口，与本次遗留无人释放锁不同。

确认项在公共 `RedisTransactionLockSupport` 一处修复，密码重置和树写锁都接入。异步命令的结果以不因线程中断取消的方式等待；结果确定后若线程已中断，先尝试释放本次实际取得的锁并等待结果，再失败退出。正常成功仍注册 afterCompletion，注册失败立即清理；释放也不因中断标记丢弃结果。没有新增配置、租约、重试队列或后台补偿。

非等待重置仍不排队竞争锁；树写锁保留等待前一持有者的行为。中断情况下会等待获取结果确定，而不是立即丢弃结果。三个重置入口的门禁、调用顺序、键空间、10015 占用响应和提交后交付窗口不变。

## 本地代码轨

外评核实和修复后，主代理独立只读核对最终实现、调用方与测试：

- 获取前检查真实事务、同步回调和已有中断；不在不具备释放边界时发送命令。
- 中断不会取消获取 Future；实际取得锁后保留释放责任，原线程等待释放结果，不在其他线程用错误 owner 解锁。
- 正常提交、回滚和结果未知仍经 afterCompletion 释放；注册失败清理。异步获取失败不伪装成 10015，不解他人的锁；释放失败不覆盖原异常或既有事务结果。
- 三个重置入口及两个身份域键保持，租户内重置和平台首管理员恢复仍共用目标用户键；没有恢复独立强制下线或其他暂缓功能。
- 同族扫描覆盖生产 Redisson 锁调用：密码重置、树写锁共同接入；JobAppServiceImpl 使用 JVM ReentrantLock，不属于本次异步结果丢失模式，不扩改。
- 公共类替代原两处相同的事务释放流程，只有既有阻塞/非等待两种调用模式，不引入通用锁框架或运行时开关。

当前无未处置 P0–P3；存疑待用户决策项为零。中断请求等待结果确定后再退出的行为及树锁等待取舍已明确写入现行设计。
