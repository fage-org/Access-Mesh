# 权限授予记录级属性编辑方案（决策记录）

> 状态：已确认（confirmed，2026-08-08）
> 文档性质：决策记录；不再作为实现依据
> 当前权威设计：[`docs/design/frontend/permission-grant.md`](../design/frontend/permission-grant.md)（v3.1 记录级聚焦编辑）
> 确认后的处理：已回写权威设计（permission-grant.md + api-contract.md §6.5.2）；创建任务并实施；实施完成后归档本文

## 1. 背景与问题

当前授权弹窗以“操作 + 范围”为编辑上下文：选择一个操作后，在资源树中勾选多个资源，并通过一组共享的“条件 / 允许再授予”控件设置授权属性。

这种交互适合批量赋予完全相同的权限，却不能表达以下常见场景：

| 角色 | 操作 | 资源 | 条件 | 再授予 | 子权限 |
|---|---|---|---|---|---|
| R | VIEW | A | 条件 C | false | A 专属子权限 |
| R | VIEW | B | 无条件 | 可独立设置 | B 专属子权限 |

具体问题如下：

1. 当前弹窗修改条件或再授予后，会把设置统一应用到当前操作下所有已勾选的已有授权及新增授权。
2. 已存在的异构设置可以在“不触碰授权设置”时保持，但不能在同一弹窗中分别编辑。
3. 子权限的数据模型已经按父授权记录挂载，当前界面也提供“挂载到主权限”选择，但它与资源级属性编辑分离，用户不容易理解三个属性属于同一条父授权记录。
4. 因此，界面表现出来的编辑粒度小于数据模型实际支持的粒度。

## 2. 已核实的数据语义

### 2.1 主权限记录

MANUAL 直接授权的身份键为：

```text
(角色, 资源或 ALL 范围, 操作, 父权限)
```

前端业务键可表示为：

```text
(resourceTypeCode, resourceCode, codeType,
 operationCode, scopeMode, parentPermissionId)
```

其中：

- 主权限的 `parentPermissionId/dependOn` 为空。
- 子权限的 `parentPermissionId/dependOn` 指向具体父授权记录。
- `conditionCode` 和 `canGrant` 是授权记录的可变属性，不参与身份唯一性。
- 同一角色、资源/范围、操作、父权限下最多存在一条有效 MANUAL 记录。

因此，A/VIEW 与 B/VIEW 本来就是两条独立记录，可以分别保存不同的条件、再授予和子权限。

### 2.2 子权限

子权限通过 `depend_on` 精确挂载到一条父授权记录，不是挂载到角色、操作或资源类型的公共分组。

本提案不改变已经确认的子权限收窄规则：

- 子权限不承载条件设置。
- 子权限不允许再授予。
- 子权限仍可按父记录分别配置。
- 子资源类型仍受 `SUB_PERM` 配置约束。

### 2.3 条件与再授予约束

同一条授权记录不能同时“有条件”且“允许再授予”：

```text
conditionCode != null  =>  canGrant = false
```

这不影响不同资源分别配置。例如 A/VIEW 可以有条件且不可再授予，B/VIEW 可以无条件并按授权传递规则设置 `canGrant`。

### 2.4 多来源 OR 语义

记录级配置不等于最终权限一定被收紧。权限查询按多来源 OR 语义合并：

- A/VIEW 的某个直接来源有条件；
- 但 A/VIEW 又通过其他角色、ALL、资源继承或其他来源获得无条件授权；
- 则最终 A/VIEW 仍可无条件生效。

界面可以编辑 MANUAL 直接记录，但不应让用户误以为修改单条记录必然收紧所有有效来源。

## 3. 方案目标与非目标

### 3.1 目标

1. 条件、再授予、子权限统一归属于当前聚焦的父授权记录。
2. 支持同一角色、同一操作下，不同资源分别保存不同属性。
3. 保留资源树批量勾选的效率；属性修改逐条进行，批量效率由**显式复制**（§4.4）承担，不做隐式覆盖。
4. 保持现有后端记录模型和 `apply-grant-plan` 提交协议。
5. 已有异构授权打开后原样展示、原样保存，不发生隐式迁移或覆盖。

### 3.2 非目标

1. 不允许同一角色、同一资源/范围、同一操作、同一父权限并存多条不同条件的 MANUAL 记录。
2. 不改变“条件权限不可再授予”规则。
3. 不恢复子权限的条件或再授予能力。
4. 不在本方案中改变权限查询的 OR 合并语义。
5. 不把继承来源或 AUTO_DEP 来源变成可编辑记录。
6. 不在未确认前修改后端接口、数据库或当前权威设计。

## 4. 推荐交互方案：记录聚焦编辑 + 显式复制

### 4.1 页面结构

资源树继续负责选择“是否存在这条授权”，授权设置区负责编辑“当前聚焦记录的属性”。

```text
┌ 授权 ─────────────────────────────────────────────────────┐
│ 操作权限  [查看（VIEW）                              ▾]   │
│                                                          │
│ 资源                                      □ 全量（ALL）   │
│ ┌──────────────────────────────────────────────────────┐ │
│ │ ☑ A资源          [条件 C] [不可再授予] [子权限 2]   │ │
│ │ ☑ B资源          [无条件] [可再授予]   [子权限 0]   │ │
│ │ ☐ C资源                                             │ │
│ └──────────────────────────────────────────────────────┘ │
│                                                          │
│ 当前授权：A资源 · VIEW · INSTANCE                        │
│ 条件       [条件 C                                  ▾]   │
│ 再授予     □ 允许再授予                                 │
│ 子权限     [配置当前授权的子权限]                        │
│                                                          │
│ [复制当前设置到…]                                              │
└──────────────────────────────────────────────────────────┘
```

### 4.2 基本操作

1. 选择操作后，资源树展示该操作下所有直接授权现状。
2. 资源勾选框只控制授权的新增、保留、撤销，不再隐含统一属性覆盖。
3. 聚焦某个已勾选资源后，授权设置区只读取和修改该资源对应的授权记录。
4. 聚焦 A，选择条件 C，只更新 A/VIEW。
5. 聚焦 B，保持无条件，只影响 B/VIEW。
6. 点击“配置当前授权的子权限”，子权限天然挂到当前 A 或 B 记录，不再要求用户在进入后重新理解公共父记录列表。
7. ALL 作为独立虚拟授权记录，拥有自己的条件、再授予和子权限入口。

### 4.3 新勾选资源

新勾选但尚未配置属性的资源需要一个明确默认值。本提案建议：

```text
conditionCode = null
canGrant = false
children = []
```

用户聚焦该资源后可以独立修改。**D2 已确认（§11.1）：不引入“新增授权默认模板”，固定使用上述默认值。**

### 4.4 显式复制（决策 D3 修订：保留显式复制，替代批量按钮与彻底移除两方案）

**2026-08-08 最终结论**：不采用"批量应用到已勾选资源"或"仅逐条编辑"，使用**显式复制**——默认只修改当前聚焦记录，批量效率由"复制当前设置到目标资源"承担：

1. 源 = 聚焦记录的条件 + 再授予；未聚焦时入口禁用。
2. 用户显式点击"复制当前设置到…"后，在弹窗中**显式选择目标资源**（当前已勾选的 MANUAL 主记录，可多选）。
3. 确认摘要展示目标数量与目标值，目标已有异构设置（条件/再授予不同）时明确标注将被覆盖。
4. 条件非空时目标 `canGrant` 自动为 false（对齐 20041 不变量）。
5. **默认不复制子权限**（子权限按父记录独立配置，避免复制歧义）。
6. 只复制到 MANUAL 直接记录；AUTO_DEP 与继承来源保持只读。
7. 复制为独立动作，生成目标记录各自的 update 草稿（目标为本次新增记录时属性=复制值而非默认值），不改变焦点，不产生任何隐式覆盖。

示意：

```text
将 A 的设置复制到以下 7 条已勾选授权？
条件：工作时间
再授予：否（子权限不复制）

其中 3 条已有不同设置，确认后将被覆盖。
```

## 5. 树节点与焦点交互备选

树节点当前存在“整行点击切换勾选”的既定行为，而记录级编辑还需要“聚焦当前资源”。两种动作如果都绑定整行会冲突，必须选择一种交互。

### 方案 A：复选框切换，整行聚焦（推荐讨论起点）

- 点击复选框：新增或撤销授权。
- 点击节点其他区域：聚焦该授权并显示记录设置。
- 优点：焦点模型清晰，适合继续扩展条件、再授予和子权限。
- 代价：改变当前“整行点击即可勾选”的便捷行为。

### 方案 B：整行继续切换，增加“设置”入口

- 点击整行：继续新增或撤销授权。
- 点击节点末尾的“设置/详情”按钮：聚焦并编辑记录。
- 优点：保留现有勾选习惯。
- 代价：节点操作更密集，移动端和长名称场景可能拥挤。

**D1 已确认（§11.1）：复选框切换、整行聚焦 + 上下文聚焦。**

## 6. 子权限交互调整

### 6.1 推荐入口

子权限入口放在“当前授权记录”设置区，标题明确展示父记录：

```text
配置子权限
挂载到：A资源 · VIEW · 条件 C
```

这样可以直接表达：子权限属于 A/VIEW，而不是属于操作级共享设置（旧模式）。

### 6.2 多父记录切换

（决策前备选——**D6 已确认（§11.1）采用“记录设置区直接进入、单父记录上下文”，本下拉方案不实施**）如果仍保留独立子权限配置页，可保留“挂载到主权限”下拉框作为快速切换能力，但默认值必须是进入前聚焦的父记录。切换父记录后，资源树应重放该父记录自己的子权限状态。

### 6.3 SUB_PERM 相邻问题

目前子权限资源类型选择器可能展示后端 `SUB_PERM` 不允许的类型，直到保存时才报错。**D5 已确认（§11.1）：同期补授权专用只读契约（api-contract §6.5.2）并前端过滤**，方案如下：

- 新增授权专用只读接口，按父资源类型返回允许的子资源类型；
- 前端过滤或禁用不允许的类型，并展示无可选类型空态。

这是相邻契约问题，不应通过前端硬编码允许集解决。

## 7. 草稿与提交语义

核心提交协议无需改变，前端草稿应从“操作级共享设置”调整为“记录级设置”。

| 用户动作 | 草稿结果 | 提交结果 |
|---|---|---|
| 勾选未授权的 A | A 的 `add` | `creates[]` 新增 A 记录 |
| 修改已有 A 的条件/再授予 | A 的 `update` | `updates[]` 按 A 的记录 ID 更新 |
| 取消已有 A | A 的 `remove` | `removes[]` 删除 A；其子权限随父级联移除 |
| 恢复刚取消的 A | 撤销 A 的 `remove` | 不提交删除 |
| 给新 A 添加子权限 | 子 `add` 通过 A 的草稿父关联 | A 的 `creates[].children[]` |
| 给已有 A 添加子权限 | 子 `add` 通过 A 的持久化 ID 关联 | 子 create 带 `parentPermissionId` |

必须保持以下规则：

1. 修改 A 不得产生 B 的 update。
2. 仅勾选或取消资源，不得隐式修改其他已存在记录的属性。
3. 只有显式复制才能同时生成多条 update。
4. 新增父记录与其子权限仍在一次 `apply-grant-plan` 请求中原子提交。
5. 弹窗取消时，本地记录级草稿全部丢弃，不泄漏到页面变更清单。

## 8. 现有数据与兼容性

1. 不需要数据库迁移；当前表结构已经按记录保存条件、再授予与父子关系。
2. 不需要改变 `apply-grant-plan` 的 creates/updates/removes 结构。
3. 已有 A/B 异构记录首次打开时分别回显，不再使用一个“混合态控件”代替记录值。
4. 历史子权限的条件和再授予字段继续兼容只读，不由本界面隐式清理。
5. AUTO_DEP 记录仍为只读；同键 MANUAL 记录可独立新增和编辑。

## 9. 有效权限提示

为了避免把“编辑直接记录”误解为“最终权限一定如此”，可在当前记录存在其他有效来源时展示提示：

```text
该资源在当前角色已加载来源中仍有无条件 VIEW 来源；当前条件不会收紧当前角色的有效权限。
```

建议提示来源包括（**限定当前角色已加载来源，D4 已确认**）：

- ALL 权限；
- 资源继承或操作覆盖；
- AUTO_DEP 或其他无条件来源。

是否在本次改造中实现该提示，需要结合现有列表接口能否提供完整来源判断，见 D4。**D4 已确认（§11.1）：同期实现，提示限定“当前角色已加载来源”，不声称用户级最终权限。**

## 10. 验收场景草案

### 10.1 核心场景

1. 同一角色、同一 VIEW 操作，A 设置条件 C，B 保持无条件；提交后两条记录分别正确。
2. A 有条件时 `canGrant=false`；B 无条件时可以按授权传递校验独立设置 `canGrant=true`。
3. 修改 A 的条件不产生 B 的 update 草稿。
4. A、B 分别配置不同子权限，提交后 `depend_on` 分别指向正确父记录。
5. 新增 A/B 后只配置 A，B 使用已确认的新增默认值。
6. 已有 A/B 设置不同，打开并直接确认不会统一覆盖。

### 10.2 复制与边界

1. 显式复制时准确展示影响数量与目标值，并为每条目标记录生成独立 update（目标为本次新增记录时生成 add + 复制值）。
2. AUTO_DEP 与继承来源不会被复制（只读、不在目标范围）。
3. 复制默认不携带子权限；目标子权限仍按父记录独立配置。
4. ALL 与 INSTANCE 分别编辑，互不错误覆盖。
5. 取消或恢复授权时，属性草稿与子权限草稿保持一致。
6. 删除有子权限的父记录时，继续提示子权限随父移除。
7. 条件记录存在其他无条件来源时，展示限定于"当前角色已加载来源"的提示（D4 同期实现）。
8. 子权限资源类型只允许选择 `SUB_PERM` 允许集（D5 同期实现；请求携带角色业务键，mode/reason 判定与写校验同口径）。

| 编号 | 决策问题 | 选项 |

| D2 | 新勾选授权的属性默认值是什么？ | A. 固定无条件且不可再授予；B. 支持可见的新增默认模板 |

| D6 | 子权限入口放在哪里？ | A. 当前记录设置区直接进入；B. 保留公共入口并默认聚焦当前父记录 |

### 11.1 决策结论（2026-08-08 产品确认）

| 编号 | 结论 | 补充决定 |
|---|---|---|
| D1 | **A. 复选框切换、整行聚焦** | **上下文聚焦**：矩阵打开自动聚焦 initial 资源（未授权也聚焦，设置区只读展示默认值）；任意资源行可聚焦；焦点为空时首次勾选自动聚焦，焦点非空时批量勾选不抢焦点；取消勾选焦点记录 → 焦点清空 |
| D2 | **A. 固定无条件且不可再授予** | 新勾选资源不继承设置区当前值；不引入"新增默认模板" |
| D3 | **显式复制** | 默认只修改聚焦记录；"复制当前设置到…"：源=聚焦记录的条件+再授予，目标=已勾选 MANUAL 记录显式选择+确认覆盖，不复制子权限，条件非空时目标 canGrant=false；无任何隐式覆盖 |

### 11.2 补充确认（2026-08-08，均已回写权威设计）

- **基线、焦点与草稿**：baseline 使用 `includeChildren=true` 一次加载主权限与子权限，来源链只消费 `dependOn==null`；焦点对应 MANUAL 编辑槽位，`initial` 使用完整授权键；取消勾选采用 suspended 双路径，重新勾选可恢复；ALL 选中后聚焦 ALL 槽位，取消 ALL 后回到 INSTANCE 并清空焦点。
- **显式复制与摘要**：复制只覆盖显式选择的已勾选 MANUAL 目标，不复制子权限；add 就地修改、update 合并且不得同一 id 多条，`after==before` 时删除无差异草稿；源条件停用时禁用复制；已勾选、待撤销和无条件记录都显示相应摘要。
- **条件规则**：条件规则在租户内可读，不设置 CONDITION:VIEW 读取门禁；新选择只允许启用条件，历史停用绑定在未修改时允许保留；主权限的条件与再授予不变量分别由 20041/20042 兜底。
- **子权限规则**：`SubPermissionPolicy` 统一解析顶层或嵌套通配、并集、大小写与 reason；候选区分加载中、加载失败、配置不一致三态；子权限固定 `conditionCode=null`、`canGrant=false`，非法 create 或任意 update 返回 20043，历史异常记录仅允许读取和删除。
- **后端契约与架构**：授权方案使用单一 apply-plan；旧 save/revoke/children/add-child/remove-child 端点在迁移完成后删除；Java 预检方法为 `prevalidate(plan)`；`resolveSubPermissionPolicy(...)` 是策略唯一公开入口，读写共用；授权域内仅允许 PlanDomainService → GrantDomainService 单向复用校验，事务仍由 AppService 声明。
- **实施与联调**：T-FE-040 采用 mock-first、纯 reducer 单测和人工 mock 场景验收，不新增组件测试基础设施；T-FE-018 负责真实接口联调；T-PERM-034 与 T-PERM-041 分别承接子权限策略/20043 与主权限 20041/20042，依赖关系和索引已同步。
