# 租户开通与独立平台运营

本文承接 [Q-063](../pending-problems.md#q-063)。设计与实施已完成，任务及验收见 [归档计划](../archive/2026-10-08/tenant-lifecycle-plan.md)。本文为当前权威契约，身份边界同时归位于 [Gateway 设计](services/gateway.md#platform-tenant-boundary)。

## 已确认边界

依据：2026-10-07 Q-063 启动指令、平台身份方案选择与平台账号管理范围确认。

- 平台运营者不代客户管理，不以平台身份进入租户维护用户、组织、角色或业务授权；首管理员密码重置为明确允许的凭据恢复例外，范围见下文。
- 建立独立于租户的平台账号、登录与权限体系；租户 1 保持普通租户，不以租户 ID 为平台特权依据。
- 执行中未确定的产品行为、设计取舍与范围须交用户决定；候选方案不视为已采纳。

<a id="platform-accounts"></a>
## 平台账号管理范围

已采纳目标：多个独立平台账号，账号同权，均可管理租户和平台账号；首期不提供平台角色与细分权限分配。平台账号操作记录应区分真实操作者，不能以共享平台管理员身份代替各账号身份。

平台账号管理保护最后一个启用管理员，拒绝使数据库中启用的平台账号归零。临时登录失败锁定不计入该保护，也不因其他账号被临时锁定而禁止启停操作；锁定仍按原期限自动到期（2026-10-07 用户确认）。该保护仅针对独立平台账号，不据此宣称租户内 Q-059 的最后管理员问题已解决。

平台账号管理写事务采用 READ COMMITTED 并按平台账号管理锁串行；等待锁后重新验证操作者状态。锁查询必须清理 MyBatis 会话缓存，不能将锁前缓存的启用状态当作锁后最新状态。

首个平台管理员通过部署环境变量创建，仅首次初始化生效，重启不覆盖存量密码。后续新增账号与管理员重置密码均生成随机密码、展示一次，并强制首次改密；其他仍可登录的平台管理员可以重置账号，全部失联时按部署方离线恢复规程处理。首期平台账号只停用和恢复，不提供删除；停用与密码重置均使旧会话失效。已采纳范围不改变上节“平台运营者不代客户管理”的约束。

<a id="tenant-admin-handoff"></a>
## 新租户首管理员交付

新租户开通时由系统生成随机初始密码，仅在开通成功时展示一次，由运营线下交付。客户首次登录必须修改密码，复用现有强制改密流程。运营会接触初始密码，这是所选交付方式的明确边界；不提供代登录或代管理入口。

平台与租户账号的强制改密都要求新密码与当前密码不同；不得原样提交初始密码以解除 forceResetPwd。普通自助改密的既有规则保持不变（2026-10-07 用户确认）。

密码只以哈希持久化，不进入操作日志、后续详情或查询响应。当前租户 1 的 bootstrap 密码形态是实现基线，不据此将新租户初始密码改为固定值或环境变量共享值。

平台始终可以重置租户首管理员密码，不以是否已完成首次改密为限制，操作必须审计。此能力是“不代客户管理”的凭据恢复例外，限定为首管理员，不开放任意租户用户密码重置或业务管理。开通响应丢失也经明确的重置操作恢复，不借初始化重试覆盖密码。审计记录真实平台操作者、目标租户与目标首管理员，不记录密码。

新增的平台账号密码重置和平台重置租户首管理员密码，在数据库与审计提交后同步清除对应账号的登录失败计数，解除临时登录锁定；清除失败不得返回恢复成功，可以再次显式执行恢复。其余既有租户内重置入口不据此扩大修改（2026-10-07 用户确认）。

平台恢复仅重置凭据，不恢复首管理员的启用状态或角色；账号已被删除时明确拒绝。首管理员仍由客户按既有账号／角色生命周期管理，不新增保留账号保护，不以本任务关闭 Q-059（2026-10-07 用户确认）。

<a id="tenant-management"></a>
## 租户运营范围

首期提供开通、列表、详情、修改名称、停用、恢复及上节限定的首管理员密码重置。不提供租户删除，不复用租户编码。停用保留租户业务数据与审计记录，不隐式清理用户、角色、授权或服务凭证。

<a id="tenant-login"></a>
## 租户登录切换

登录入参一次性从 tenantId 切换为 tenantCode，由服务端解析内部租户 ID。租户编码创建后不可修改，展示名称可修改；所有租户均在运营开通时指定编码。租户 1 与 `default` 无特殊绑定，`default` 仅是可选普通编码；“租户 1 固定 default”已由首次部署仅建平台账号的方案取代（2026-10-07 用户确认）。

旧 tenantId 登录入参停止接受，不保留兼容期；前端旧会话要求重新登录，缺租户身份的历史草稿不再回落租户 1。内部数据关联和可信身份传递继续使用 tenantId，tenantCode 不替代内部主键。

租户编码长度为 1～64，以小写字母开头，其余字符只允许小写字母、数字和连字符；大小写不自动转换。校验表达式为 `[a-z][a-z0-9-]{0,63}`。中文名称通过独立展示名称承载，不能作为编码。

普通管理台登录与 OAuth2 客户端解耦：直接以 tenantCode、用户名、密码及既有验证码认证，不再依赖 `sys_oauth2_client` 的客户端记录，也不逐租户预建 `admin-web` 客户端。OAuth2 授权与令牌通道保持独立，继续使用各租户自行注册的客户端及既有客户端安全校验。

既有 clientId 登录字段仅保留为可选审计来源标签（最长 128），不能影响身份或授权；登录日志仍可展示调用方声明的来源。未知租户编码与错误账号／密码对外同码拒绝，不向租户登录日志写入虚构租户 ID。

租户首次强制改密由后端执行：尚未改密的原生用户会话只放行必要的自助认证／改密入口，不允许进入业务 API，也不签发该用户的 OAuth2 委托令牌。强制改密完成后旧会话失效、重新登录；普通自助改密保留既有会话行为（2026-10-07 用户确认）。

<a id="frontend-realms"></a>
## 前端身份入口

沿用现有前端项目，不另建部署站点。平台使用独立登录页与运营布局，仅承载租户管理、平台账号和平台审计；租户登录页输入租户编码，继续使用既有业务管理界面。

平台和租户的令牌、路由门禁与页面状态分别维护，同一浏览器可以分别登录；任一身份登出、过期或改密不得误清另一身份的会话。平台身份不通过入口切换获得租户业务访问能力。

<a id="tenant-initialization"></a>
## 首次部署与租户初始化

首次部署只创建独立平台账号，不自动创建 default 或其他租户；全部租户从运营台开通。当前固定租户 bootstrap 须拆出参数化租户初始化能力，不再作为启动时自动创建租户 1 的入口。

新租户使用统一标准模板：基础类型与操作、系统配置、默认组织、首管理员 admin、管理角色、菜单和接口映射同事务创建，任一步失败整体回滚。不复制其他租户的实时运营数据，不提供自定义初始化模板。

重复 tenantCode 拒绝创建；响应丢失先查询是否已开通，再经首管理员密码重置恢复交付，不将重试解释为覆盖存量租户。沿用仓库空库重建政策，不新增存量库在线迁移或模板版本升级工具；实际环境重建仍由环境负责人按备份与重建规程执行，任务实现本身不删除部署数据。

<a id="tenant-seed-storage"></a>
## 初始化种子的技术落点

基础类型、操作与系统配置种子保留在同一权威 DDL，改成接收租户 ID 的 PostgreSQL 初始化函数 `initialize_tenant_baseline(tenantId)`。建表时仅定义函数、不执行种子；Java 开通事务调用函数后复用参数化固定图建立管理员、组织、角色、菜单及映射。函数仅承载静态基础种子插入，不承载平台鉴权或业务编排；不另建服务内种子副本。

<a id="platform-audit"></a>
## 平台审计

平台审计独立落表，记录真实平台账号、目标租户或账号、动作及结果，仅平台运营界面查询。开通、启停、平台账号管理和密码重置的关键数据库变更与对应审计记录同事务，审计写入失败则变更回滚。

平台账号不冒充租户用户，不向现有 operation_log 写入虚构租户身份。平台日志不得包含密码、密码哈希、服务密钥或完整请求体。管理编排中的失败尝试由既有操作日志切面在主事务结束后独立写平台审计；明确失败记 FAILURE，门禁结果未确认记 PENDING，失败审计不可用不覆盖原拒绝原因。Redis 发布与数据库提交不属于同一原子事务，审计须区分已提交的数据库变更与门禁就绪结果，不把尚未成功发布的启用状态表述为访问已恢复。

<a id="platform-data-boundary"></a>
## 平台身份与数据接入边界

平台账号 `platform_account` 与租户注册表 `sys_tenant` 是平台主数据，不含所属 tenant_id；平台审计 `platform_audit_log` 的 target_tenant_id 表达被操作租户，不表达操作者所属租户。表结构唯一权威仍为 [schema](schema/access-service.sql)。上述主数据是独立平台身份的范围性例外，不改变租户业务表必须带 tenant_id 的规则。

平台身份采用独立认证域，不能复用租户用户编号或其权限投影。平台端点只接受已认证、仍启用、凭据代次匹配的平台账号，强制改密账号仅可访问自身认证和改密入口；同权平台账号无需租户 QueryGate 计算，租户业务端点仍完整执行既有 QueryGate 门禁。平台端点清单必须显式登记，租户会话、OAuth2 委托令牌、服务凭证与内部密钥均不能代替平台账号认证。

凭据代次与租户会话代次绑定到单个令牌会话或单条 OAuth2 链，不能只写在同账号共享会话中；否则重新登录写入的新代次会使旧令牌复活。租户初始化仅在受控种子作用域内写目标租户事实，平台操作者另记平台审计，不冒充租户主体。

平台专属端点不进入租户 bootstrap 的接口映射或授权图；Gateway 与服务端共用精确平台端点清单，走独立平台认证。租户能力包承载租户主数据与运营编排，平台账号留在 auth 能力、独立审计留在 audit 能力，初始化仍由 bootstrap 专属通道维护。

<a id="tenant-suspension"></a>
## 租户停用与恢复

停用成功后，AccessMesh 控制的登录、已有会话请求、服务凭证调用、OAuth2 入口和新启动的租户任务立即拒绝，不允许依赖缓存自然到期才生效。已经进入执行的请求或任务不强制中断。

恢复后，用户必须重新登录；停用前的 OAuth2 访问令牌和刷新令牌继续失效。服务凭证若自身仍启用且未过期则恢复可用，不因一次租户暂停而强制轮换。

上述契约限定于 AccessMesh 控制的入口，不承诺撤回外部系统离线接受的 JWT 或已执行的数据变更。具体检查点、事务并发边界与故障处置机制必须在实施前明确，不把缓存失效广播等同于立即停用。

<a id="redis-gate"></a>
## Redis 即时门禁

已采纳方向：共享 Redis 即时门禁；不采用每次正常租户请求都经 Gateway 回源数据库的方案。Redis 不可信时拒绝访问、自动核对数据库重建，以及单主部署范围均已确认。

### 一致性与故障恢复协议

- 数据库保存租户状态和会话代次；Redis 承载共享运行时门禁，不在服务或 Gateway 的 L1 中保存可放行状态。
- 同一租户的状态变更与门禁修复共用数据库行锁。取得锁后，先在 Redis 预置拒绝记录并取得仅本次操作持有的发布令牌，再读取租户最新事实；旧数据库读取结果不能用来创建新的发布令牌。停用先完成此预阻断，再提交数据库停用及会话代次递增；预先阻断失败不得继续变更或返回成功。数据库提交失败时保留保守阻断，由修复流程重新核对数据库。
- 恢复先保持阻断并提交数据库启用，再凭本次发布令牌发布 Redis 状态；令牌已被后续操作替换、记录消失或 Redis 进程已改变时拒绝发布。修复同样按行锁、预阻断、最新事实读取、发布的顺序执行，避免旧恢复或旧修复覆盖新停用；放行发布失败不得宣称恢复完成。
- 门禁读与写在 Redis 脚本内核对实际进程标识；运行时状态绑定生成它的进程。重启后即使加载了旧持久化快照，旧进程的启用记录也不能放行。门禁状态缺失、格式非法或进程不匹配均视为未知。
- 租户原生 token 同时绑定签发时 Redis 进程标识；校验会话时原子读取门禁与当前进程。任何 Redis 重启后，旧原生会话均须重新登录，即使门禁已从数据库重建也不能复活改密前被撤销的会话。OAuth2 继续验证数据库密码指纹及租户代次，平台账号继续验证数据库凭据代次（2026-10-07 用户确认）。
- 故障策略：Redis 不可用或状态未知时拒绝新租户请求和任务；未知状态由 access-service 持租户行锁从数据库重建，不在门禁未知期间使用旧权限快照放行。正常流量只读 Redis，数据库读取发生在状态变更和修复时。
- 首期部署范围：沿用当前单主 Redis，不承诺 Sentinel/Cluster 自动故障切换的强一致性；恢复旧备份或切换实例需要阻断流量并重建门禁后再开放。运行时门禁是生命周期协调状态，其协议不得以普通业务缓存 TTL 或失效广播替代。

共享协议实现由 [T-ACCESS-092](../archive/2026-10-08/tasks/T-ACCESS-092.md) 承载。发布令牌同时绑定租户与 Redis 进程；只允许将本次仍存在的阻断记录发布为启用或停用状态，记录丢失不能由旧发布操作直接重建。新用户会话与 OAuth2 授权链携带会话代次；正常用户访问要求租户启用且代次匹配，服务凭证访问只消费租户启停状态并继续执行凭证自身校验。

自动修复采用有界分页巡检：每次扫描至多 200 个租户，以一次 Redis 批量读取识别未知状态；修复按租户 ID 顺序批量加行锁（SKIP LOCKED）、预置阻断后批量读取最新事实并发布，不按租户循环查询数据库。正常用户请求只读 Redis。多实例争抢时未取得的锁交由后续巡检处理；异常不改变业务请求的拒绝状态。

### 机制核实

2026-10-07 使用本机已存在的 `redis:7-alpine` 镜像启动无网络、无宿主端口的临时容器：Lua 中读取 `INFO server` 的 run_id、核对门禁记录后返回 READY；保存记录并执行 SAVE、重启容器后返回 UNTRUSTED。容器随后停止并自动删除。该实验仅验证进程标识可识别重启恢复的旧记录，不是完整一致性或业务回归证明。

依据：[Redis INFO](https://redis.io/docs/latest/commands/info/)提供进程标识；[持久化说明](https://redis.io/docs/latest/management/persistence/)说明快照恢复可能丢失近期更新；[复制说明](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)明确异步复制及 WAIT 不保证故障切换时强一致。当前仓库 Compose 仅配置单个 Redis 实例，未配置 Sentinel/Cluster。

| OAuth2 客户端 | client_id 全局唯一，当前 SQL 将 admin-web 等客户端种入租户 1；不能逐租户原样复制 | [权威 schema](schema/access-service.sql) |

本设计记录已确认的产品契约，采用不代表实施已完成。实施状态与剩余验收以[计划](../archive/2026-10-08/tenant-lifecycle-plan.md)和[任务看板](../tasks/README.md)为准；后续出现新的行为取舍仍须先由用户决定。

API 字段与错误码登记于[契约总册 §26](access-service-api-contract.md#contract-section-26)，表结构与参数化模板以权威 DDL 为准。所有身份均通过各自认证入口建立：平台账号不进入租户 OAuth2 委托链，不创建租户用户投影；租户原生会话必须携带单令牌代次与强制改密标记。缺少这些标记的旧会话直接失效。
