> 本稿为已采纳的实施方向：资源同步与依赖声明保持独立，SDK 协调可选；保留写时物化，来源按需解释，不建立逐种子逐完整路径的持久 support。原完整路径存储、强制两步接入和跨 owner 手工 override 口径由本稿取代。

<a id="scope"></a>
## 1. 目标与范围

业务系统声明“授予资源 A 的某操作时，同时授予资源 B 的某操作”。平台在写事务中计算角色的自动权限，运行时消费普通授权行，不遍历依赖图。

例：REPORT/sales-monthly:VIEW → REPORT/sales-template:VIEW。角色显式获得月报查看权后自动获得模板查看权；撤销月报后，模板若无其他来源则回收。A 与 C 都依赖 B 时，撤销 A 不回收仍由 C 支持的 B；独立 MANUAL B 也不由自动回收删除。

**权限含义**：自动权限可独立使用，depend_on=NULL。它不表达“仅访问 A 时临时使用 B”；现役 depend_on 子权限/主资源上下文是另一模型，不在本稿合并。源权限的运行时互斥结果也不构成目标权限的用途限制。

### 1.1 已采纳原则

- 资源与依赖接口各自可用，不强制一个大清单。原有单资源 sync 与按类型范围 full-sync 保持；无依赖的接入方不加载 manifest、不配置依赖发布、不提交空依赖集合。
- 有依赖需求的接入方独立发布声明。SDK 可选协调资源准备与依赖发布，不替换成熟同步程序，不将两个 HTTP 请求称为原子事务。
- 保留 declaration 源事实、compiled 依赖图与 AUTO_DEP 授权结果分层。
- 按角色完整计算 desired 再与 actual diff；不以持久路径计数判定存续。
- 取消 role_permission_auto_support 表、全路径补录、support 回填及专属一致性检查。按需解释和对账复用同一推导函数。
- AUTO_DEP 只读、不可转授；普通管理员主要在角色授权页操作，依赖页面向诊断。
- v1 不提供跨 owner 或平台内部目标的手工 override。服务凭证、类型所有权与既有门禁继续生效。

### 1.2 保持的边界

实例级、同 owner 服务、单操作触发、条件直传与多条件 OR、同步物化保持。类型级 scope_all/AUTHORITY_ROOT 不作种子；父实例继承得到的权限不展开为种子。授权页直接说明边界。

API 与操作关联派生仍归 T-PERM-054，不通过依赖图授 API 绕过启动门禁；菜单可见性走既有投影。跨系统 export、类型级依赖、注解扫描、异步重建、多操作 AND 触发不进入本次范围。动态 SQL 消费仍归 T-PERM-036。

<a id="architecture"></a>
## 2. 总体架构

```text
仅同步资源的系统 → resource-entity/sync 或 full-sync → 资源事实
有依赖的系统 → permission-manifest/full-sync
              → permission_dependency_declaration（业务键源事实）
              → DependencyCompiler
              → resource_dependency（已解析图，单写者）
              → 角色种子 + 共享推导函数
              → role_resource_permission（AUTO_DEP，事务内 diff）
              → PermQueryEngine（消费授权行）

来源解释 / 对账 → 一致的种子、图与实际授权
               → 同一推导函数 → 共享推导图 / desired 与 actual 比较
```

资源删除引起的依赖失效与自动权限回收由平台内部触发。调用方只调资源 sync 也必须得到完整收窄行为，不要求额外发布 manifest 才撤掉旧授权。

<a id="data-model"></a>
## 3. 数据职责

正式 DDL 以 [schema/access-service.sql](schema/access-service.sql) 为唯一权威，声明、编译与发布状态已随 071 实现，自动授权结果已随 072 物化落地。

### 3.1 声明事实 permission_dependency_declaration

保存租户、声明来源、稳定声明键、源/目标业务键和操作码、编译状态/原因；当前 manifest revision 由同 tenant + service 的 service_manifest_sync 保存，声明行不重复存储。源触发操作至多一个，NULL/空集合表示任意操作触发；目标操作集合非空。类型/操作码与 codeType 宽度对齐现契约，codeType 维持 64 字符边界。

状态为 RESOLVED/REJECTED；原因保留 CROSS_OWNER、RESOURCE_MISSING、TYPE_MISSING、OPERATION_INVALID、SELF_DEPENDENCY、CYCLE。失败行保留用于诊断，由重新提交重驱动，不增加 PENDING/resolver。

MANIFEST 为依赖声明唯一写入来源，范围按 tenant + 服务身份隔离，管理面拒改删；不提供 ADMIN_UI 手工声明通道，同 owner 也不例外（M3，2026-09-20）。业务键复用 BusinessKeyUtil，sync 协议键走 SyncKeyCodecUtil。

### 3.2 摄入状态 service_manifest_sync

保留 tenant + service、发布代次、revision、规范化 payload_hash、SUCCESS/PARTIAL/FAILED、is_dirty 与最近同步时间。发布代次由发布源可靠递增，平台持久校验新旧；revision/hash 用于重复提交识别，不代替发布排序（§4.4）。

先执行发布代次校验，旧代次不得以相同内容绕过拒绝。通过代次校验后，只有 revision 相同、hash 相同、上次项级全 RESOLVED 且非 dirty，才能语义无变化短路；较新代次内容相同也须推进发布排序状态。资源/类型/操作定义等非 manifest 变更影响声明或图时，同事务置 dirty；重新判定后刷新状态，不能以历史 SUCCESS 掩盖当前缺失。

### 3.3 编译图 resource_dependency

仅 DependencyCompiler 写。保留源/目标实体、触发位与目标操作位，补目标反向索引以定位受影响角色。诊断 declaration_id 不代表聚合边唯一来源。

编译键为源实体 + 目标实体 + COALESCE(source_operation_bits,0)；同键 RESOLVED 声明的目标操作取并集，任一声明变化按键重编译。真实来源按键查询，删除不按诊断字段定位。

auto_grant 已随声明通道退役，后端 DTO、前端请求/表单/列表及契约已同步移除；旧接口与错误码 20048 均退役。声明来源仅保留 MANIFEST，不实现 ADMIN_UI 写入分支；旧数据处置见 §5。

### 3.4 自动授权结果

复用 role_resource_permission：grant_source=AUTO_DEP、单 canonical 操作位/行、can_grant=false、depend_on=NULL、条件按推导变体保留。每角色的自动结果仅按资源、canonical 操作与条件身份精确去重，不按操作覆盖或条件宽窄压缩（§6.3）。既有唯一性允许 MANUAL/AUTO_DEP 并列，多条件变体落库仍须对照 DDL 验证。

不新增 support 表，不把推导图/路径列表塞入授权行 JSON。grant_dep_id 不作存续或清理依据；单字段不能表达多来源，已定案保留不写不读（2026-09-21，Q-022 留观），物化器永不写入。

<a id="integration"></a>
## 4. 独立接入与可选协调

### 4.1 资源同步独立可用

资源单条与 FULL 接口保持独立，现役字段与错误语义见契约总册 §19；资源同步组件已实现 §4.4 的发布代次及完整空清单协议，依赖生命周期与物化回收仍按任务卡验收：

| 接口 | 粒度 | 行为 |
|---|---|---|
| POST /api/access/resource-entity/sync | 一个资源 | UPSERT / DISABLE / DELETE |
| POST /api/access/resource-entity/full-sync | 当前租户 + 来源服务 + 一个资源类型的完整同步范围 | 清单内 upsert；清单外该同步范围旧事实软删；完整空清单清空该同步范围 |

FULL 不是“批量修改几个资源”，也不按类型扫描删除其他维护来源。类型、编码、可选名称/状态与必填 syncVersion 均是现役要求，没有因自动授权新增。

简单系统新增 D 只发 D 的单条 UPSERT；首次导入可 FULL 提交完整 REPORT 清单。不需要理解依赖或安装 registration starter。资源删除与自动授权的收缩由平台按触发面闭合，不推给调用方额外发依赖来撤权；仅停用/恢复资源不改变自动授权传播（§7）。

### 4.2 依赖声明独立发布

端点 POST /api/access/integration/permission-manifest/full-sync 接收 schemaVersion/revision/dependencies 及 §4.4 的发布代次，不含 resources；正式字段名与类型在契约总册登记。身份来自凭证，不信任请求体 serviceCode。静态 JSON 与请求 DTO 同构；动态 PermissionManifestProvider.dependencies() 只产依赖，不强迫返回资源目录。

声明沿用 source 业务键/操作与 requires 目标集合，例如 REPORT/sales-monthly 的 VIEW 要求 REPORT/sales-template 的 VIEW。资源可由既有同步程序预先登记，不要求每次依赖发布都重传全部资源。

FULL 代表该服务完整依赖声明；完整空依赖集合表示清空该范围，读取失败/分页未完不能伪装为空。畸形清单预检零副作用；合法项级失败沿 SyncResultResp 风格返回，HTTP 200 不等于全部成功。

语义 hash 按规范化 declarationKey 与 source/target 业务键、操作集合计算：操作排序去重、NULL/空触发等价、声明按完整 canonical bytes 总排序后以 UTF-8 SHA-256 计算。description 不计入语义 hash，但其更新不得被短路吞掉；展示字段独立更新规则在正式契约中钉清。幂等条件见 §3.2。

### 4.3 SDK 协调是可选便利

复用已有服务凭证及 perm.credential-id/credential-secret/allow-insecure。registration starter 已提供独立 manifest 发布（契约 §19.10.1），可选择“先准备资源、再发布依赖”的门面；单租户与 TenantRegistrationProvider 多租户隔离维持，不再建另一套密钥配置。

协调方法接收明确的资源输入或复用接入方同步程序，不从依赖边猜完整资源目录。单条增量与按类型 FULL 均独立可用；只改依赖时可仅发 manifest。

不强制资源+依赖大文件，也不要求两个接口携带同一 revision：资源项仍用 occurredAt+sequenceNo，manifest revision/hash 标识清单。资源前置失败/部分失败或真正旧发布代次时给出诊断并停止；同代次同指纹已确认的增量重试使用 PUBLICATION_UNCHANGED，可继续。依赖失败重试既定发布输入，不拼接重新扫描后的另一个快照。SDK 本地仅校验形状/重复键/自依赖/清单内环，资源/操作存在性、所有权与完整图由服务端验证。

### 4.4 动态发布与顺序协议

动态 Provider 的显式消费面为 SDK PermissionRegistrationPublisher.publish：调用方一次取得不可变 publication（代次、revision、依赖清单），发布及重试都传该对象，不在重试时再次调用 Provider。静态 JSON 启动发布须配置与该文件绑定的代次；仅在启用 manifest 发布时要求相关配置。示例服务提供显式调用样例与可选启动配置，默认不发布依赖；不能为了演示改动其 Gateway 承担鉴权的现有架构。无依赖接入不装 registration starter；不预建队列、定时器或通用工作流。

**FULL 发布排序已定（M1，2026-09-20）**：资源 FULL 与依赖 manifest FULL 均采用发布源确定的可靠递增代次，平台按各自范围持久记录并原子校验，拒绝旧代次。资源范围为 tenant + sourceService + resourceType，manifest 范围为 tenant + 服务身份；两条通道独立，不要求共用代次。新副本以代次 42 发布 {A,B} 后，旧副本代次 41 的 {A} 晚到，必须在任何事实写入及缺失删除前拒绝，不能删 B 或回退依赖。每项资源 syncVersion、git revision 与内容 hash 均不能替代该协议。

代次绑定发布快照，由能确定快照先后的发布源分配；重试沿用原代次与原发布输入，禁止旧副本重试时临时申请新代次或用本机 now() 把旧目录包装成新版本。同代次内容冲突不得覆盖；同代次合法重试仍须支持既定部分失败与 dirty 重判，不得把失败冒充成功。业务回滚须作为新的发布快照分配更高代次，不能恢复旧代次写入。

**FULL 与增量共同排序已定（M1，2026-09-21）**：混用 FULL 的资源 scope 中，增量与 FULL 都必须携带发布源确定的可比较顺序；平台双向防护，既不让较早 FULL 删除随后新增的资源，也不让延迟增量重建较新 FULL 已清理的事实。纯增量 scope 可以继续使用现役协议；混用范围的增量调用方须升级。平台事务锁不能替代源侧发布顺序；不采用每次 FULL 都要求调用方暂停变更并排空增量的方案。

正式字段、源侧代次责任、同代次完整内容比较、部分失败与增量交错、客户端切换见下节及契约 §19.2.1/§19.10。资源共序与 manifest 发布组件已实现并验证并发、部分失败重试及事务回滚；资源/定义生命周期接线、保全迁移与可选 SDK 已实现，071 已于 2026-09-21 收口。未知部署库不自动执行迁移。

#### 4.4.1 资源发布顺序协议

正式字段登记于契约总册 §19.1/§19.2。每个 tenant + sourceService + resourceType scope 保存是否已切入顺序协议、最近接受的 FULL 代次及完整请求 hash、已接受请求的最大代次；每个同步业务键保存最近成功代次与请求指纹。失败的单条请求不推进这些值，技术异常使状态与事实共同回滚。

- **源侧责任**：代次与资源事实在同一可靠提交顺序中分配并持久保存。一次源事务可给多个不同资源事件相同代次，但同一资源/代次只能对应一个最终事件。FULL 在一致快照切点保留独立代次，该快照包含切点之前的完整源事实。源侧数据库事务序列或既有可靠事件位置可承担此责任，单纯自增取号后再无保护地扫描目录不成立。SDK 接收已绑定快照的代次，不自行生成。
- **增量拒旧按键判断**：请求代次必须大于已接受 FULL 的代次；再与本业务键最近成功代次比较。其他资源更大的增量代次不阻止本键尚未应用的事件。例如 B:43 先到、A:42 后到，在无 FULL 42 及以上屏障时两者均可应用。相同键/代次/指纹为幂等 no-op，相同键/代次内容不同为冲突；旧代次不写事实或账本。
- **FULL 拒旧按范围判断**：新 FULL 代次必须严格大于该范围已接受请求的最大代次。例：增量 B:43 已成功，晚到 FULL 42 整请求拒旧，不能删除 B，也不部分应用其余项。已接受 FULL 的同代次、同完整请求 hash 允许重试，但存在后来成功的增量或 FULL 时，该旧 FULL 重试也拒旧。修复来源必须采集新的完整快照，再取得新代次，禁止给旧请求换号。
- **保留逐键 syncVersion**：代次防跨请求回退，occurredAt/sequenceNo 仍防同资源版本回退。新代次增量的 syncVersion 必须严格更新；FULL 可携带未变化资源的相等版本并作无写入确认。若 FULL 的逐键版本更旧，或相等版本却要求改变现有事实，该项报告版本冲突、不写该项；不能把输入矛盾冒充已应用。相等版本的比较使用资源写入的规范化有效值，不能因 JSON 键序或可选字段未传误报变化。
- **部分失败**：完成身份、scope、结构、完整请求指纹及范围代次检查后，合法 FULL 即使逐项有业务失败，也同事务推进 FULL 屏障并记录 PARTIAL。成功项与缺失清理保持既定语义；失败项没有成功版本。原快照同代次重试可恢复依赖已补齐的失败项，成功项不重复变更。后来有新请求成功则不能再重放旧 FULL，须发布新快照。抛出的异常整事务回滚，屏障也不推进。
- **指纹**：FULL hash 包含全部请求业务字段（含名称、状态、extra、syncVersion 与来源元信息），排除代次本身，items 按完整业务键排序；同键重复在任何写入前拒绝，JSON 对象键排序、数组保持语义顺序、值不作有损转换。省略与 null 仅在现役写语义相同时归一。manifest 仍另存语义 hash 用于图短路，完整请求 hash 用于同代次不可变性，两者不可混用。
- **一次性切换**：无顺序状态且未携带代次的纯增量 scope 按现役规则处理。首个成功应用的带代次增量，或通过范围预检并被接受的 FULL（含 PARTIAL），在同一事务内建立顺序状态，此后该 scope 的无代次请求全部拒绝，不自动退回旧协议。接入方切换前只需一次性排空旧客户端在途请求并升级该 scope 的全部写者；首次 FULL 使用新采集快照，旧事实作为其校准基线。切换后 FULL/增量可以并发，不要求每次停源。事务回滚不留下半切换状态。

manifest 的范围是 tenant + 服务身份，与资源范围代次独立；同代次完整 hash 冲突拒绝，旧代次零副作用拒绝，合法项级 PARTIAL 推进排序屏障，原代次原快照可重判 REJECTED/dirty，较新代次覆盖后旧重试拒绝。description 变更必须通过新代次发布；语义 hash 不变可以复用已编译图，但必须保存展示字段与新排序状态。

**完整空资源清单已定（M1，2026-09-20）**：允许明确提交 items=[] 表示该 scope 的完整空快照。身份、类型所有权及发布代次校验通过后，仅软删当前 tenant + sourceService + resourceType 对应 sync_metadata 范围内的同步事实；不按类型扫删其他维护来源，不影响其他租户、服务或类型。沿资源删除触发面同事务收缩依赖贡献及受影响自动授权，其他有效来源支持的下游授权保留，无需客户端再发 manifest 才撤权。

调用方读取失败、分页未完成或 Provider 异常不得转换为空清单提交；缺失/null items 不等于明确的完整空快照。旧代次空清单仍零副作用拒绝；新代次校验不能识别业务方误报为空，SDK/接入说明须明确完整性责任。资源 DTO 已接受明确空数组，缺失/null 返回 HTTP 400；资源事实清理与依赖贡献生命周期已由 071 落地，自动授权回收已由 072 挂接（资源 DELETE/FULL 缺失删除同事务重算收缩）。

## 5. 声明编译与写权限

格式预检 → 源类型 SYNC 且 owner=声明服务 → 目标同 owner → 资源/操作存在 → 自依赖 → 与已提交图联合判环。服务声明不得指向平台内部类型或无服务 owner 的 MANAGED 类型，API 也不作目标。拒绝声明不产生边，已有声明降级时移除对应贡献。

原 resource-dependency/batch-sync 随 manifest 通道退役；DEPENDENCY:SYNC、bootstrap 行、前端 perms/routes/mock、SDK、契约与 autoGrant 全字段链同步清理。存量来源/跨 owner 边须核实实际部署数据，不能以仓库无种子推断运行库无数据。

## 6. 角色级物化与共享推导

### 6.1 种子

该角色有效 MANUAL 行中取 scope_all=false、实例 ID 非空、depend_on=NULL 的行，条件不限。不按用户当前有效角色或运行时条件预删种子；物化处理角色授权事实，主体、条件与互斥仍由引擎运行时判定。

不展开父继承、不以 AUTHORITY_ROOT/类型级授权作种子，也不以它们覆盖目标权限为由压制已推导的 AUTO_DEP；本次未扩展种子边界。

资源 status 不参与种子、目标或中间节点的传播过滤；资源停用时既有及新产生的合法推导仍按相同规则计算。资源软删、授权撤销与声明变化继续触发重算，不能将停用与删除混同。

### 6.2 逻辑闭包

一致视图批量装载种子、图与操作定义，多角色重算共享图；通过既有 DomainService 供给数据，不绕过能力边界另查 Mapper。

```text
逻辑事实键 = (资源, canonical 操作, 条件变体)
种子入队，每个新增事实处理一次
源有效位满足边的触发操作 → 推出目标操作并沿用条件
同事实去重、不同条件保留
闭包稳定 → 按完整事实键精确去重 → desired AUTO_DEP → 与 actual diff
```

effectiveBits=binaryBit|inheritMask 复用 OperationPermissionUtils。触发至多一个操作，NULL 触发表示任意有效操作；直接推导关系记录实际触发操作，不能混用不同类型的位空间。

条件随实际触发事实传递：A:VIEW 无条件、A:EXPORT 带 C，只有 EXPORT 派生 B:READ 时，B 必须带 C。C1/C2 按 OR 并存，不能取其一或变 NULL。同一资源和操作的 NULL 与带条件变体也同时保留，不按条件支配删除；逻辑推导、物化与解释使用相同事实键，不枚举完整路径。

### 6.3 精确去重与互斥

**M2 已定（2026-09-20）**：保留实际推导出的各操作事实，只合并同角色内资源、canonical 操作、条件身份完全相同的自动事实。不同操作不因覆盖关系删行；不同条件身份不因表达式相似或宽窄关系合并，NULL 与窄条件变体均保留。MANUAL 与 AUTO_DEP 来源仍可并存，不因手工行或类型级授权覆盖而省略推导结果。接受较多授权行，以精确事实去重控制重复，不实施覆盖反链或额外的压缩算法。

互斥继续沿现有引擎的 canonical 操作与入口评估集合语义。UPDATE 覆盖 VIEW 且两者均被推导时，两行均参与各入口既有过滤；若满足条件后的同一互斥评估集合包含规则两端，按既有规则两端剔除，不能先删除 VIEW 来规避冲突。此选择是自动授权的行为定案，不宣称与旧覆盖压缩方案等价；操作覆盖仍用于触发匹配和运行时权限匹配，不用于压缩物化结果。

`AutoGrantEngineContractPgIT` 已用真实 PostgreSQL 与 PermQueryEngine 验证候选 AUTO_DEP 结果行：不同操作的无条件/有条件身份不串义、NULL 与多个条件变体并存及 OR、独立 MANUAL 存续、非传递/相互覆盖、单查/批查/LIST 的互斥集合差异。例如 UPDATE 覆盖 VIEW 且两行存在时，VIEW 查询两端同场而拒绝，UPDATE 查询只收集 UPDATE 而允许，LIST 两端被剔除；不能将此简化为两个操作都必然拒绝。该测试直接装配候选结果；依赖推导、共享来源撤销与传播的真实写链路验收已由 072 的 AutoGrantMaterializationPgIT 补齐（真实写入口 + 真实 PG/Redis）。

上述场景已由 072 真实引擎验证（不同操作 NULL、不同行条件 OR、无条件与窄条件来源、共享来源撤销、非传递/相互覆盖；PERM_MUTEX 单查/批查/LIST 由 078 AutoGrantEngineContractPgIT 校准）。中间事实均继续传播，不因另一操作覆盖而停止。小图和互斥组件测试只能说明局部性质，不能替代上述验证。

#### 6.3.1 推导与撤销的可检验预期

以下 C1/C2 是不同条件身份，不在物化时求值；NONE 表示无条件。每个结果写完整事实键，列表没有全路径计数。该表已由 072 共享核心单测逐行验证并作为真实写链路的输入输出要求，078 的引擎测试校准这些结果的消费。

| 种子与图 | 完整 desired AUTO_DEP | 后续变更的预期 |
|---|---|---|
| A:VIEW/C1 → B:READ，B:READ → C:VIEW；D:VIEW/NONE → B:READ | B:READ/C1、C:VIEW/C1、B:READ/NONE、C:VIEW/NONE | 撤 D 仅移除 NONE 变体；撤 A 后自动结果为空；中间 B 在两次计算中都必须继续向 C 传播 |
| A:VIEW/C1 → B:READ；D:VIEW/C1 → B:READ | B:READ/C1 一条事实、两条直接支持边 | 撤 A 保留 B；撤 D 才删除 B，不按物理授权 ID 或单个 grant_dep_id 清理 |
| A:VIEW/C1 → B:READ；D:VIEW/C2 → B:READ，C1/C2 表达式相同 | B:READ/C1 与 B:READ/C2 | 两条件身份必须保留；条件相等性不由表达式判断 |
| A:VIEW/NONE 与 A:EXPORT/C1；仅 EXPORT → B:READ | B:READ/C1 | 不得从同资源的无条件 VIEW 借用 NONE |
| AUTO B:VIEW 与独立 MANUAL B:VIEW/NONE 并存 | AUTO 按图独立存在 | 撤完自动来源只删 AUTO，MANUAL 仍存在；不以 MANUAL 覆盖为由提前压缩 AUTO |

同一事实从多个种子到达时，入队与展开最多一次，但记录每个不同的直接前驱关系；因此共享来源解释可回溯到所有显式根。资源级 DAG 与精确事实去重共同保证终止，不能依赖枚举完整路径的深度上限。重算 always 从当前全部 MANUAL 种子开始，旧 AUTO_DEP 不作种子，避免失去来源的环状自持。图编译本身仍拒资源环。

### 6.4 diff、撤销与条件回收

desired 为存续依据；多来源不按路径计数。来源改变后完整重算，无来源的自动行同事务删除，独立 MANUAL 行不由物化删除。

INLINE 维持“一个 MANUAL 属主 + 多个系统派生引用”，用户不可显式共享。授予撤销/资源删除/类型级联/角色删除先收集候选 conditionId，完成自身删除与重算后，事务末尾按实际引用归零回收。不能提前回收，也不能因派生引用尚存而跳过后无人再处理。

### 6.5 来源图不持久化

解释时同一函数收集逻辑事实间的直接推导边与显式种子，构成共享 DAG。节点由逻辑事实键定位，不依赖物理 AUTO_DEP ID，以支持显式种子及 desired/actual 漂移诊断；不再构造覆盖压制节点。根来源与条件变体不能丢失。写时不保存完整路径，不引入等价替身表。

取消 support 不取消授权 diff 审计、事务、锁或引用回收。完整历史推导回放不在解释承诺内，历史变更继续使用既有审计。

| 类型删除级联 | 回收声明、边、自动授权与条件孤儿 |
| 角色删除 | 回收角色授权及条件孤儿（拍板 A：全部有效授权行含 AUTHORITY_ROOT——角色删除成为授权根第二回收路径，仅删所有者角色时触发，registry 2026-09-21），不重算已删角色；全部删除通道一致（管理面 deleteRoles/组织容器角色级联/角色同步 DELETE 与 FULL 漂移），已删角色不作种子、其 AUTO_DEP 按 desired 恒空回收、不构成操作引用（外评 2026-09-21 补全） |
| 条件编辑/删除 | 维护引用与受影响结果，条件判定保持运行时语义 |

binaryBit 变更/操作删除存在有效 MANUAL/AUTO_DEP 授权引用时拒绝；AUTHORITY_ROOT 专属基座仍按现役 T-PERM-062 的同事务迁移/删除处理，不将系统基座误算为用户引用而锁死所有自定义操作。声明的操作编码引用在定义变更时重编译：删除后按 OPERATION_INVALID 降级，位变更无有效授权引用时按新位重编译，inheritMask 变更重编译/重算。引用拒绝码 20069 已随 072 在正式契约 §12.1 登记（granted_bits 等值口径，AUTHORITY_ROOT 豁免）。非 manifest 入口影响声明/图时置 dirty；仅资源 status 切换不因自动授权置 dirty。

**资源停用/恢复已定（M1，2026-09-20）**：停用不充当自动撤权动作。源、目标或中间资源停用均不暂停传播，既有自动授权保留；恢复无需重建自动权限或额外发布 manifest。撤销显式种子、删除资源或修改依赖时仍按完整 desired 重算收缩。此决定只规定自动授权事实与传播，不改变资源自身的运行时鉴权语义，不承诺停用即所有鉴权入口拒绝访问，也不放宽来源服务停用后的同步入口门禁。

资源新增不因 scope_all 自动派生；REJECTED 通过重发恢复，不设隐式 resolver。资源删除后恢复并重传，同 revision 不得被历史 SUCCESS 错误短路。

071 的编译生命周期已接入：资源单条 DELETE/FULL 缺失删除、资源类型所有权变更/删除、操作位或 inheritMask 变更/操作删除，在原事务与 RESOURCE_ENTITY 锁内调用共享编译领域服务。按受影响服务批量装载声明和事实，只重判 RESOLVED，保留 REJECTED 等待显式重发；类型删除按声明业务类型引用回收，含已失去解析 ID 的拒绝行。非 manifest 变更置 dirty，不改变原发布代次/hash；启停资源和操作名称/同值更新不置 dirty。合法声明限定外部 SYNC 类型：实际资源删除入口是资源同步通道，MANAGED 管理面、内部投影和 API 资源不能产生合法声明引用。授权物化与操作引用拒绝已随 072 接入（六入口接线 + 物化器 PgIT 验证）。

## 8. 并发与事务

MANUAL diff、编译影响、AUTO_DEP diff、INLINE 回收与变更标记在对应写事务内完成，中断整体回滚。缓存走既有 afterCommit，刷新窗口沿入口现契约，不宣称提交等于所有快照立即刷新。

共享串行边界复用租户 RESOURCE_ENTITY 树写锁，资源发布、manifest 编译、MANUAL 授权变化及全部会收缩自动授权的写入口均在读取推导输入之前取得此锁，持有到 afterCompletion。不另设编译锁、逐角色锁或持久推导版本。目标树锁族全序固定为 SYS_ORG → ABSTRACT_ROLE → SYS_MENU → RESOURCE_ENTITY，需要更早树锁的入口先取得它们；持有 RESOURCE_ENTITY 后不得再请求前面的树锁。角色重算按 ID 升序批量处理以固定写入顺序，正确性由共同租户锁保障。

**M4 的必要反例**：授权读旧图 A→B，新种子未提交；编译删边时查不到该角色，不取其角色锁；授权随后提交旧图派生 B。只说“编译锁→已发现角色锁、授权仅角色锁”不能证明撤权一致性。

TypeDefinitionAppServiceImpl.deleteTypesByIds 的混合 resource_type/role_type 批删已统一为 ABSTRACT_ROLE → RESOURCE_ENTITY，与组织/角色投影事务顺序一致；单测旧实现失败，MixedTypeDeletionLockPgIT 以真实事务/Redis 锁及取锁闸门验证这处顺序。该测试镜像组织投影的锁序，不代替完整组织 API 验收。071 其余编译入口已按矩阵逐调用点核对；072 级联扩展（六入口）已接线核对（apply-grant-plan 新增 RESOURCE_ENTITY 锁、角色删除补 ABSTRACT_ROLE→RESOURCE_ENTITY 全序）。

上述共同边界使授予事务与删边事务必有先后：授予先提交时编译侧能发现并重算该角色；删边先提交时授予侧只能读到新图。不能先读取种子或图、只在写入 AUTO_DEP 前取锁；不能只锁反查已发现的角色。沿现役树锁的 READ_COMMITTED、Redis 不可用拒写与 watchdog 已接受边界，不引入另一套锁设施。

| 写入口族 | 共同锁前置位置 | 本事务闭环 |
|---|---|---|
| apply-grant-plan / 系统种子及显式授权清理 | 读取被改授权与推导输入之前；已有高序树锁按全序先取 | MANUAL 改动、AUTO_DEP diff、条件孤儿回收、审计与 afterCommit 标记 |
| manifest FULL / 资源 sync、FULL、资源移除 | 代次/所有权复核与声明、资源、图装载之前 | 版本状态、编译聚合、受影响角色完整重算 |
| 资源类型/操作/所有权变更 | 锁内重绑类型身份，读取依赖/授权引用之前 | 引用拒绝或重编译与重算；类型授权根按既有生命周期处理 |
| 角色/主体/组织/菜单删除及本地投影级联 | 先取得入口需要的 SYS_ORG/ABSTRACT_ROLE/SYS_MENU，再取得 RESOURCE_ENTITY；随后读取授权和依赖引用 | 被删角色不重建自动行，其余受影响角色完整重算 |
| 条件编辑/删除与 INLINE 属主回收 | 读取授权引用/准备删除条件之前 | 保持条件身份直传，最后按真实剩余引用回收 |

矩阵已由 071/072 逐个实际调用点核对（含内部领域调用；bootstrap 固定图为内部类型不入依赖图，无需接线）。提交闸门已覆盖未提交新种子遇到删边（AutoGrantMaterializationPgIT M4 用例）与定义/资源删除交错；对账不代替正常事务保证。

### 10.1 旧依赖保全与执行门禁

[迁移脚本](../ops/auto-grant-migrate-071.sql)与[执行手册](../ops/runbook-auto-grant-migration.md)已交付，并用真实旧表夹具验证。当前工作区未提供可连接的应用数据库，不宣称已迁移任何部署环境。部署时的实际盘点是脚本执行前置，必须在停止旧版本写入后重查，开发期间的报告不能替代这次核对。

- 新安装直接采用新 schema；升级使用单事务脚本，先检查旧表形状与迁移目标是否冲突，任何不符中止且零修改。
- 旧 resource_dependency 原表整体保全为 resource_dependency_legacy（含软删行、原 ID、auto_grant、来源及审计字段）；仅重命名必要索引，禁止把它当成新编译表、禁止自动生成 MANIFEST。新的 resource_dependency 是编译器专属空表，使用独立的新唯一索引/反向索引；活动模型不再含 auto_grant。旧数据保全表不被新运行时/编译/物化读取，只供迁移诊断。
- 若迁移前存在任何有效 AUTO_DEP 授权，或其他无法确认已停用的自动授权存量，脚本在改表前中止，保留全部事实和版本。部署方必须核查来源与处置，不能为了启动新版本而自动删授权、自动清空 grant_dep_id 或把它们伪造为 MANUAL。此门禁作为脚本行为与回归用例交付，不要求本任务操作未提供的部署库。
- 原 autoGrant=false 依赖仍是保全历史；所属服务通过新凭证独立发布 manifest 才产生生效声明，平台不代发。旧 ADMIN_UI/SDK_SCAN 等来源不进行静默类型转换，不恢复手工写入口。
- 071 必须用旧 schema 夹具覆盖空库、有 ADMIN_UI/其他来源旧边、有软删行以及有效 AUTO_DEP 的迁移：前两类保全后能够发布新声明，最后一类中止后 schema/事实原样保留。新旧程序不能并行写入改名后的表；回退须先停止新程序，并依据备份/迁移记录检查新声明与授权，不能直接覆盖回旧 schema。

部署核查与数据处置由有该环境权限的部署方执行，目标任务交付可验证的迁移程序和手册，不包含对未知环境的上线或数据清理。

manifest 不需要用户 API 快照/固定图授权行；管理 explain 需注册固定图及管理门禁。batch-sync/autoGrant 已从管理路由、旧服务方法/DTO、后端实体/响应、新 schema、前端及权限种子移除；严格 Jackson 下不再接受旧字段回传。运行数据迁移先核实，不能假设没有历史边。

## 11. 按需来源解释

计划 POST /api/access/resource-dependency/explain 仅解释“为什么生成该角色的自动权限”。角色使用业务键，维持 DEPENDENCY:VIEW 类型级管理门禁，不开放服务凭证，不恢复已删除的通用用户排查端点族。

一致性视图读取种子、编译图、操作定义与 actual AUTO_DEP，同一推导/精确去重函数输出 desired 的共享关系、显式来源、条件与操作触发说明，并对比实际存储；操作覆盖解释用于说明为何满足触发，不用于说明删行压制。漂移必须标识，不能把“应生成”当成“已生效”。

完整路径按需展开，可分页/截断且标识；不得截断物化事实计算。窄条件、无条件来源及无物理授权行的中间节点均可解释。它不证明用户当前角色有效、条件成立、互斥通过或 Gateway 缓存刷新。

解释与预览的事实读取使用 AppService 的 REPEATABLE_READ、readOnly 事务，在单次请求中通过无缓存的领域读取端口批量装载角色种子、图、操作、条件身份与实际 AUTO_DEP。管理门禁继续走现有 PermQueryEngine，不绕过引擎查授权表；推导输入不用可能分别过期的运行时快照缓存。事务只覆盖本次读取，结束后不保留跨请求快照。返回 viewedAt 与截断标记，不将多次请求拼成原子快照。

解释输出共享逻辑 DAG 与直接支持关系，不返回全路径枚举列表。无 target 全集视图仅含参与推导的种子（2026-09-21 定案 B：未命中依赖边的显式授权不进图，防孤点淹没推导链）。界面选定目标事实后沿直接边按需展开来源；maxDepth/maxNodes 只限制输出，完整 desired 仍先由共享核心算出；target 模式下选定事实保底入选输出节点——截断只挤祖先，不把查询目标本身挤出输出（2026-09-21 贴回外评拍板）。达到限额必须标记 truncated 并报告总节点/边数量，不能因没显示某条路径就显示“无来源”。完整路径展示是用户选择一条链的展开，不计算所有根到目标的路径组合。

正式字段与管理门禁登记于契约 §12.3.1；不新增来源表、跨请求游标状态或历史推导事件库。

> **落地注记（T-PERM-073，2026-09-21）**：explain 已实现（契约 §12.3.1 落地状态注记）；前端入口按用户定案仅依赖页查看器（授权页 AUTO_DEP 维持「由资源依赖自动补全」标注，完整 DAG 浏览集中在依赖页——registry 2026-09-21）。

<a id="admin-ui"></a>
## 12. 管理台任务

角色授权页分组展示显式与自动权限，自动项只读，来源定位到显式授权。授/撤展示自动增减影响与仍被其他来源保留的结果；复用推导/精确去重，不在前端另算图。

**预览与保存已定（M5，2026-09-20）**：预览仅供参考，界面明确提示结果可能因并发授权或声明变更而变化。保存以服务端事务内最新事实重新校验权限、计算完整结果并提交；仅因自动影响与预览不同，不拒绝保存，也不要求再次预览确认。不新增强制预览凭证、预览版本匹配或预览结果锁定，既有权限门禁、不变量校验、受影响行数断言和失败回滚保持。

例：A/C 均支持 B，预览撤 A 时显示 B 由 C 保留；保存前 C 已被撤销，则保存撤 A 同时回收无其他来源的 B。保存成功后前端刷新实际权限与来源，不把旧预览继续展示为提交结果；刷新失败须明确显示结果暂未刷新，不能伪称旧预览已生效。预览计算失败或数据不全应标识无法预览，不能展示为零影响；预览失败本身不取代或绕过正常保存校验。

预览入口为角色授权族的 preview-grant-plan，复用保存的 ROLE:MANAGE 门禁、角色有效性与委托/形状验证，不额外要求 CONDITION 写权限。计划解析与校验已提取为纯准备入口 prepare（T-PERM-073 落地）：包含 create 的新建及 update 的就地编辑/换绑新建，INLINE 以负数合成 ID 暂挂，保存阶段才由 prevalidate 执行对应 INLINE 写入并应用（不先真实写再回滚）；两入口共享校验，禁止另写宽松预览算法。

现有 INLINE 的就地编辑沿用 EXISTING 身份，只在预览内覆盖条件定义，不新分配身份。新 INLINE 条件在预览中以请求条目位置区分身份（例如 creates[0] 与 updates[1]），即使表达式相同也不合并；未分配物理 conditionId，不调用序列、不落库、不产生权限变更标记。共享推导事实的条件身份须同时支持已存 ID 与预览临时身份。保存重新准备并生成实际 ID，预览键不作为提交凭证。一次性一致视图采用 §11 的只读事务；其余正式字段见契约 §11.4.1（已落地），不承诺从预览到保存的数据冻结。

当场提示“独立目标权限”及类型级/父继承不触发边界。依赖页显示服务、同步状态、失败原因、源/目标及影响角色，revision/编译来源放详情。依赖页只读，移除手工新增、编辑、删除及旧批量同步入口，不提供同 owner 编辑或跨 owner override；变更提示指向所属服务的 manifest 发布流程。
