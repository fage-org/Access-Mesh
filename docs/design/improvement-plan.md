# AccessMesh 项目诊断与完善计划

> 版本: v2.0 | 日期: 2026-06-06 | 状态: 待审查

## 1. 背景

本文档基于项目作者与 AI 的多轮对话，系统性诊断当前项目的不满意点，并制定分阶段完善计划。

项目定位：**开源通用权限管理平台**（面向中小型企业），用于验证权限管理设计思路。代码均为 AI 生成。

---

## 2. 项目现状评估

### 2.1 完成度估算

| 层面 | 完成度 | 说明 |
|------|--------|------|
| 后端核心逻辑 | ~80% | 权限查询引擎已统一重构，核心链路通畅 |
| 后端功能完整性 | ~70% | 自动授权未实现，动态数据权限待验证 |
| 后端接口适配性 | ~50% | 接口按后端视角设计，未校准前端交互需求 |
| 前端 | ~5% | 仅有 pure-admin-thin 空壳模板，尚未改造 |
| 测试覆盖 | ~5% | 仅 permission-center 有 27 个测试，其余模块零测试 |
| 文档 | ~90% | 设计文档齐全，但实现滞后于文档 |

### 2.2 核心矛盾

**开发顺序倒置**：后端先行 → 前端后补 → 发现接口不匹配。

```
当前状态（问题）：
  UI 交互设计（空白）
      ↓
  后端 API（已实现，按后端视角设计）
      ↓
  前端（空壳模板，无法对接）

目标状态（改进后）：
  前端 UI 实现（mock 数据驱动，边设计边实现）
      ↓
  API 契约校准（前端实现暴露需求 → 后端适配）
      ↓
  前后端联调（mock 替换为真实接口）
```

## 3. 不满点诊断

### 3.1 痛点清单（按优先级排序）

| # | 痛点 | 严重度 | 影响范围 | 根因 |
|---|------|--------|----------|------|
| 1 | **UI 交互没有设计** | 🔴 阻断 | 全项目 | 复杂权限配置/查询没有参考产品，需要从零设计 |
| 2 | **权限相关接口需要逐个核对** | 🔴 阻断 | permission-center | 后端接口按后端视角设计，前端对接时会暴露参数/响应不匹配 |
| 3 | **自动授权未实现** | 🟡 高 | permission-center | 资源依赖链自动补全权限——核心差异化能力缺失 |
| 4 | **动态数据权限待验证** | 🟡 高 | permission-center | 设计有（按身份ID的数据范围），但能否适配真实场景不确定 |
| 5 | **扩展性未经检验** | 🟢 中 | 全项目 | 开源后接入者遇到未覆盖场景时能否低成本适配 |
| 6 | **CRUD/配置代码质量差** | 🟢 低 | admin-service | AI 生成的样板代码臃肿、一致性差，但不影响核心逻辑 |

### 3.2 痛点详细说明

#### 痛点 1：UI 交互没有设计

前端是一个通用权限管理平台的"脸面"，尤其是权限配置这种复杂操作，UI 交互直接决定产品的可用性。目前存在的问题：

- **简单 CRUD 场景**：可参考 pure-admin 的表格/表单模式，问题不大
- **复杂权限配置场景**：市面开源产品（若依等）仅覆盖按钮和菜单级权限，本项目的细粒度权限管理（角色→资源→操作→条件）缺乏成熟的 UI 参考
- **权限查询/校验场景**：用户需要直观看到"谁有什么权限"、"为什么被拒绝"，这类查询界面需要专门设计

**影响**：没有 UI 基准，后端接口改造没有方向。

#### 痛点 2：权限相关接口需要重新校准

当前后端接口是按"后端能实现什么"设计的，而非"前端需要什么"。主要表现在：

- 仅 CRUD 接口能满足基本需求
- 权限授予、查询、校验等核心接口的参数结构和响应格式可能需要调整
- 批量操作、树形结构、分页过滤等前端常见需求可能未覆盖

#### 痛点 3：自动授权未实现

这是权限平台的核心差异化能力。场景：

1. 用户授予角色 A"查看订单"权限
2. "查看订单"依赖"登录系统"和"查看菜单"权限
3. 系统应自动补全依赖权限，而非让管理员手动逐条授予

当前状态：`PermissionGrantAppServiceImpl` 和 `PermissionGrantDomainService` 中有 TODO 标记，`resource_dependency` 表已设计但自动补全逻辑未实现。

#### 痛点 4：动态数据权限待验证

场景示例：

- 普通员工只能查看本人的工单数据
- 团队管理者能查看本团队所有成员的工单
- 部门总监能查看本部门全部数据

当前状态：数据权限的设计已存在（条件评估、数据范围），但端到端链路（用户属性→条件解析→数据过滤）是否能适配此类场景未经过验证。

#### 痛点 5：扩展性未经检验

开源后，接入者可能遇到以下未覆盖场景：

- 接入方有特殊的权限判定逻辑（如对接外部审批系统）
- 接入方需要自定义数据权限维度（如按门店、按项目）
- 接入方的用户体系与标准设计不一致

需要确保扩展点的设计（SPI、配置、策略模式）确实可用，且有清晰的文档指引。

#### 痛点 6：CRUD/配置代码质量差

admin-service 中大量 CRUD 和配置管理接口是 AI 生成的样板代码，问题包括：

- 代码风格不一致
- 缺少必要的校验和错误处理
- 存在冗余和死代码
- 185 个文件零测试

用户对此的态度是"不核心，不费心"，但体量大影响整体质量感。

## 4. 完善计划（4 个阶段）

### 总览

```
Phase 1: 前端实现 + 后端 API 核对（边设计边实现，mock 驱动）
    │
    │  逐页面进行：设计 UI → mock 实现 → 核对后端 API → 记录改造项
    │
Phase 2: 核心功能补齐（自动授权 + 动态数据权限 + 后端接口改造）
    │
Phase 3: 前后端联调（mock 替换为真实接口）
    │
Phase 4: 扩展性验证 + 代码清理 + 文档完善
```

### 4.1 Phase 1 工作流（两阶段推进）

**第一阶段：页面盘点**。先逐项讨论确定所有页面及其承担的功能，形成完整的页面地图。

**第二阶段：逐页面设计+实现**。每个页面遵循统一循环：

```
┌─────────────────────────────────────────────────────┐
│  Step 0: 读取相关设计文档（overview / api-contract    │
│          / implementation / schema）                  │
│                                                      │
│  Step 1: 出具初步方案（布局、字段、交互、API 依赖）    │
│          与用户讨论确认后进入实现                       │
│                                                      │
│  Step 1.5: 识别可复用组件 → 提出建议 → 用户确认        │
│                                                      │
│  Step 2: Mock 数据 + 前端页面实现                     │
│  用 mock 假数据让页面可交互、可预览                    │
│                                                      │
│  Step 3: 后端 API 核对                               │
│  以 mock 中定义的请求/响应结构为基准，核对现有接口       │
│  标记 ✅满足 / 🔧需改造 / ❌缺失                     │
│                                                      │
│  Step 4: 记录 API 改造清单（本 Phase 不改后端）        │
└─────────────────────────────────────────────────────┘
```

**Step 1.5: 识别可复用组件**。每个页面方案确认后、开始实现前，检查是否存在可跨页面复用的业务模块，提出组件抽象建议，**必须与用户确认后才执行**。

**组件抽象原则**：

| 原则 | 说明 |
|------|------|
| **先确认再抽象** | 任何业务组件的提取必须先经用户确认，禁止自行决定 |
| **2+ 页面使用才抽取** | 只在至少 2 个页面中使用相同模式时才考虑抽象 |
| **不过度抽象** | 保持扁平，优先 props/slots 变体而非多层级继承 |
| **命名遵循规范** | 复用组件使用 `Re` 前缀（如 `RePermCondition`） |

**已知复用候选**（待各页面实现时确认）：

| 候选组件 | 场景 | 确认状态 |
|----------|------|----------|
| 权限条件选择器 | 权限授予（内联新建）+ 条件管理（独立 CRUD） | ⏳ 待确认 |
| 资源树选择器 | 权限授予 + 资源管理 + 权限查询 | ⏳ 待确认 |
| 角色选择器 | 权限授予 + 用户角色分配 + 组织成员分配 | ⏳ 待确认 |
| Diff 对比面板 | 权限变更日志 + 操作日志详情 | ⏳ 待确认 |

### 4.2 参考项目使用规范

`reference/vue-pure-admin/` 是实现时的权威 UI 参考（不纳入 Git）。实现前必须参考其中的同类页面。

**必须参考的内容**：

| 参考项 | 说明 |
|--------|------|
| 布局模式 | 使用 viewport 相对高度（`vh`）+ `pure-table` 的 `adaptive` 实现局部滚动，避免整页滚动 |
| 表格模式 | `pure-table` + `adaptiveConfig.offsetBottom` 让表格高度自适应视口，表体内独立滚动 |
| 树面板模式 | `el-scrollbar` + 计算高度（`calc(90vh - 96px)`）限定滚动区域 |
| 搜索栏模式 | `el-form :inline` 搜索栏，`el-form-item` 设置 `margin-bottom: 12px` |
| 图标使用 | `useRenderIcon()` + `~icons/ep/*` 或 `~icons/ri/*` 导入 |
| 样式约定 | UnoCSS/Tailwind 原子类优先；`dark:` 前缀适配暗色模式；`!` 后缀标记 `!important` |
| 组件结构 | `<script setup lang="ts">` + `defineOptions({ name })`；Element Plus 组件全局注册直接使用 |

**不应照搬的内容**：

| 不宜参考 | 原因 |
|----------|------|
| pure-admin 的权限模型（菜单/按钮级） | AccessMesh 是细粒度权限模型（资源+操作+条件），不可套用 |
| pure-admin 的 API 接口 | pure-admin 使用其内置 mock 后端，API 结构与 AccessMesh 不同 |
| pure-admin 的业务字段 | 如 `code`、`remark` 等字段需替换为 AccessMesh 的实际字段 |

**优势**：
- 先全局盘点，避免遗漏页面或功能重叠
- 每个页面实现前先读设计、出方案、经确认，减少返工
- Mock 数据结构天然成为 API 契约的草稿

### Phase 2: 核心功能补齐 + 后端接口改造

**目标**：实现自动授权，完成 API 改造，验证动态数据权限。

#### 2.1 自动授权（Auto-Grant）

**当前状态**：
- `resource_dependency` 表已设计，存储资源依赖关系
- `PermissionGrantAppServiceImpl` 中有 TODO：`自动授予依赖权限（autoGrantForInsert）`
- `PermissionGrantDomainService` / `PermissionGrantDomainServiceImpl` 中有 TODO：`自动授权解析（resolveAutoGrants）`

**实现路径**：

1. 分析 `resource_dependency` 表结构和现有依赖数据
2. 实现 `resolveAutoGrants`：根据授权资源解析依赖链，计算需补全的权限
3. 实现 `autoGrantForInsert`：在批量授权时自动补全依赖权限
4. 处理循环依赖检测（防止 A→B→A 死循环）
5. 处理依赖冲突（两个依赖路径对同一资源定义不同操作级别）
6. 区分手动授权和自动授权（`GrantSource.MANUAL` vs `GrantSource.AUTO`）
7. 撤销授权时的级联处理（手动授权被撤销时，仅当无其他路径依赖时才撤销自动授权）

#### 2.2 Phase 1 中标记的 API 改造

根据 Phase 1 产出的 API 核对清单（🔧和❌项），逐项改造后端接口。改造优先级：

1. **缺失接口**（❌）—— 前端需要但后端不存在的接口
2. **需改造接口**（🔧）—— 参数/响应不匹配的接口
3. 改造完成后回写 Phase 1 的核对状态

#### 2.3 动态数据权限验证

**场景**：按身份 ID 的数据权限筛选。

**验证步骤**：

1. 梳理当前数据权限链路：用户属性 → 条件表达式 → 数据过滤
2. 构造测试场景：普通员工（本人）、团队管理者（本团队）、部门总监（本部门）
3. 端到端测试：确认 `ConditionEvalUtils` → `PermQueryEngine` → SQL 过滤 链路通畅
4. 记录发现的缺口或问题

#### 2.4 外部系统权限查询

**场景**：接入方有外部权限系统，需要通过接口查询外部权限并合并判定。

**验证步骤**：

1. 检查当前 `PermQueryEngine` 是否支持扩展外部权限源

## 5. 执行策略

### 5.1 DoD（Definition of Done）各阶段完成标准

| 阶段 | 完成标准 |
|------|----------|
| Phase 1 | 8 个页面前端实现完成（mock 数据可交互）；API 核对清单完成（每个接口标记 ✅/🔧/❌） |
| Phase 2 | 自动授权实现 + 测试通过；🔧❌ 接口改造完成；动态数据权限链路验证通过 |
| Phase 3 | 8 个页面 mock → 真实接口替换完成，所有页面核心流程联调通过 |
| Phase 4 | 扩展点验证通过；扩展指南文档完成 |

### 5.2 质量门禁

每个 Phase 完成后必须：

1. 前端代码通过 `pnpm build` + `pnpm lint`
2. 后端代码通过 `mvn compile` + `mvn test`
3. 相关文档已更新
4. Commit 遵循 Conventional Commits 规范

### 5.3 风险与应对

| 风险 | 可能性 | 应对 |
|------|--------|------|
| mock 数据结构与真实接口差异大，联调返工多 | 中 | Phase 1 的 API 核对环节尽早发现差异，mock 结构尽量贴近现有接口 |
| 自动授权实现比预期复杂 | 中 | 先做核心路径（单层依赖），多层传递后续迭代 |
| AI 重构改偏核心逻辑 | 中 | Phase 2 涉及核心 engine 的修改以手工审查为主，AI 仅辅助 |
| 前端改造工作量超出预期 | 中 | Phase 1 按页面优先级逐块交付，不追求一次性完成 |
| pure-admin 参考项目模板与 thin 版差异大 | 低 | 仅参考 UI 交互模式，不直接复用代码 |
