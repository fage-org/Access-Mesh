## 覆盖判据排除清单（grep「路由可达」命中、不在 design_refs 的两册）

## 背景

外评 #13（定性「设计风险」，用户拍板演进）。现状：全部业务路由静态注册，菜单不可见 ≠ 路由不可达（router/utils.ts:251 注释、role-manage.md:171 等设计注记明文）；无权限用户手输 URL 打开页面壳后由各页 API 403 兜底，提示形态不一。T-PERM-037（2026-08-31）当时维持该口径的理由是「meta.auths 为前端静态声明可绕过，与后端派生方案重复」——T-FE-015 后菜单已是后端按权限派生，用 menus 树派生路由门禁不再有静态可绕过问题。用户拍板（2026-09-19）：**menus 派生路由门禁**。处置历程与修正依据见 decision-registry 2026-09-19 行。

## 范围

- store 增加会话门禁状态机与 path 集（与 T-FE-048 的统一能力刷新入口协同构建，状态机 owner 单一）。
- 路由守卫按状态机判定（uninitialized/loading → 等待；loaded → 门禁；failed → 放行兜底）。
- 显式动作路由映射表（首期仅 /perm/grant → ROLE:VIEW）。
- 各页设计文档「路由可达性」注记清扫（design_refs 全列表，含权限表效应格）。

## 当前口径

- 门禁数据源 = 后端 menus 树（权限事实）∪ 显式动作路由映射；与侧栏可见性同源不分叉，非菜单业务路由显式登记不依赖菜单。
- fail-open 仅指明确 failed 态（首载失败）：门禁失效的最坏结果=回到现状，不产生新锁死；未初始化/加载中不判放行（等待），防冷启动绕过；已 loaded 会话的刷新失败不降级状态（防一次抖动静默关掉门禁）。
- 权限热刷新（T-FE-048）联动：能力刷新成功后 path 集同步重建，门禁随会话权限即时收敛。

- 与 T-FE-053 同文件（router 守卫）：053 已完成（删 meta.roles 死分支+全 next 站点补 return+新建守卫 spec，2026-09-19 收口），本任务再加门禁逻辑（depends_on 声明）。
