## 设计摘要

### 1. 失效标记

Gateway 本地快照有两种失效方式：

| 方式 | 触发 | stale-allow 可续命？ | 语义 |
|---|---|---|---|
| 自然过期 | 主缓存 `expireAfterWrite` TTL 到期，条目转入 stale store | ✅ 可以 | 快照陈旧但未被主动撤销 |
| 显式失效 | 收到 `perm:invalidate` Redis 广播 | ❌ 不可以 | 权限中心明确告知权限已变更 |

**核心原则：权限主动撤销 > 服务不可达兜底。**

#### 标记维度

与当前 `InterfaceSnapshotCacheInvalidator.evict()` 驱逐维度保持一致：

| 事件载荷 | 标记/驱逐范围 | 说明 |
|---|---|---|
| `serviceCodes` 非空 | tenantId + serviceCode 下所有用户快照 | API mapping / 资源 / 条件规则变更 |
| `userIds` 非空 | tenantId + userId 下所有服务快照 | 用户角色关系变化 |
| 仅 `roleIds` 非空 | tenantId 级（所有用户快照） | Gateway 无法反查角色→用户，安全过驱 |

#### 三层数据结构

```
interfaceSnapshotCache: Cache<String, InterfaceSnapshotResp>   // L1 主缓存（expireAfterWrite = ttlSeconds，默认 30s）
staleSnapshotCache:   Cache<String, StaleEntry>               // L2 陈旧快照缓存（expireAfterWrite = ttlSeconds + staleGraceSeconds，默认 60s）
invalidatedKeys:      Set<String>                              // 显式失效标记集合
```

**StaleEntry 包装**：

```java
record StaleEntry(InterfaceSnapshotResp snapshot, Instant staleUntil) {}
```

- `staleUntil` = 快照首次写入主缓存的时刻 + `ttlSeconds` + `staleGraceSeconds`（默认 30+30=60s）
- stale-allow 续命时检查 `Instant.now().isBefore(entry.staleUntil())`，超时不再续命
- **为什么不用 RemovalListener 触发时刻**：Caffeine 过期清理/RemovalListener 不是严格 TTL 到点触发，可能延迟到后续访问或维护周期。若 `staleUntil` 基于触发时刻计算，实际 stale 窗口 = TTL 延迟 + grace，旧快照可能远超配置窗口仍被续命

**选择理由**：

- 主缓存使用 `expireAfterWrite`（当前行为不变），过期条目不可通过 `getIfPresent()` 获取
- Caffeine 的"过期但未驱逐"不可靠用于续命——`getIfPresent()` 对已过期条目直接返回 null
- 独立 stale store 使续命语义明确可控：主缓存过期 → 写入 stale store → stale store 再过 grace period 后自动淘汰
- `invalidatedKeys` 与 stale store 解耦，标记生命周期独立管理

#### 三层操作

| 触发场景 | 主缓存 | stale store | invalidatedKeys |
|---|---|---|---|
| 回源拉取新快照成功 | `put(key, snapshot)` | `put(key, StaleEntry(snapshot, staleUntil))`，`staleUntil = now + ttlSeconds + staleGraceSeconds` | `remove(key)` |
| 主缓存条目过期（Caffeine 自然淘汰） | 自动淘汰 | 已有数据，无需操作 | — |
| `perm:invalidate` 事件 | `invalidate(key)` | `invalidate(key)` | `add(key)` |
| stale-allow 续命检查 | — | `getIfPresent(key)` → 检查 `staleUntil` + 检查 `!invalidatedKeys.contains(key)` | `contains(key)` |
| 订阅重连全量清空 | `invalidateAll()` | `invalidateAll()` | `clear()` |

**关键设计决策：回源成功时同步写 stale store（而非依赖 RemovalListener）**

原因：Caffeine `RemovalListener` 触发时机不确定——TTL 过期后首次 `getIfPresent` 返回 null 时，RemovalListener 可能尚未执行。若此时 permission-center 不可达，stale store 中没有续命快照，stale-allow 会错误 fail-close。

回源成功时同步写 stale store 保证：
- stale store 始终**先于**主缓存过期就有数据，无竞态窗口
- `staleUntil` 基于回源成功时刻计算（`now + ttl + grace`），不依赖 RemovalListener 触发时刻
- 主缓存自然过期时 stale store 无需操作（数据已在）
- `perm:invalidate` 仍同时驱逐主缓存 + stale store + 标记 invalidatedKeys

**关键安全约束**：`perm:invalidate` 事件必须**同时驱逐主缓存和 stale store**，并**标记 invalidatedKeys**。仅驱逐主缓存而遗漏 stale store 会导致 stale-allow 续命使用已撤销权限。

#### 标记生命周期

- **创建**：`perm:invalidate` 事件触发时写入
- **清除**：
  1. 回源拉取新快照成功时清除该 key 的标记
  2. 定期清理：每 `stale-grace-seconds × 2`（默认 60s）扫描，移除不在 stale store 中的孤立 key
  3. 订阅重连全量清空时一并清除
- **上限保护**：标记集合 > stale store 条目数 2 倍时，触发全量清理（仅保留 stale store 中存在的 key 对应的标记）

### 2. 订阅恢复策略：重连即全量清空

Gateway 与 Redis 断线重连后执行：

1. **清空主缓存**：`interfaceSnapshotCache.invalidateAll()`
2. **清空失效标记**：`invalidatedKeys.clear()`
3. **后续请求按需回源**：首次请求触发 `PermissionClient.interfaceSnapshot()` 拉取新快照

**设计理由**：

- **安全优先**：断线期间错过的 `perm:invalidate` 事件无法追回（pub/sub 无持久化），全量清空确保不存在陈旧权限
- **实现最简**：一次 `invalidateAll()` 完成，无需 Redis Stream 或 offset 管理
- **惊群可控**：重连后并发回源通过 per-key in-flight 去重缓解（见 §3），避免同 key 重复远端调用；TTL 30s 兜底已默认接受同量级延迟

**重连检测**：`PermInvalidationSubscriber` 需增加重连回调：

- Reactive Redis `listenTo()` 的 `onError`/`onComplete` 触发时标记订阅断开
- 重连成功后（`subscribe` 重建）触发全量清空
- 清空操作需在主线程执行，避免并发安全问题

### 3. 与 T-GW-003 stale-allow 集成契约

T-GW-003 实现 stale-allow 时，需遵循本规范定义的三层结构和标记语义：

1. **回源成功时同步写 stale store**：回源拉取新快照成功时同时写入主缓存和 stale store，`staleUntil = now + ttlSeconds + staleGraceSeconds`，保证 stale store 先于主缓存过期就有数据
2. **续命前双重检查**：从 stale store 取出 `StaleEntry` 后：
   - 检查 `Instant.now().isBefore(entry.staleUntil())` → 超时不再续命
   - 检查 `!invalidatedKeys.contains(key)` → 已显式失效不续命
3. **续命不写回主缓存**：续命使用的快照不写回 `interfaceSnapshotCache`（避免陈旧数据覆盖未来新快照）
4. **显式失效三层同步**：`perm:invalidate` 事件必须同时驱逐主缓存 + stale store + 标记 invalidatedKeys

### 4. Per-key 回源去重

当前 `PermissionFilter` 使用手动 `getIfPresent` + 手动回源，**不存在** per-key 并发去重。重连全量清空后同 key 并发请求会打出多次远端回源。

**T-PERM-008 / T-GW-003 落地要求**：

采用 `ConcurrentHashMap<String, Mono<InterfaceSnapshotResp>>` 作为 in-flight 去重表：

```java
// 伪代码
ConcurrentHashMap<String, Mono<InterfaceSnapshotResp>> inFlight = new ConcurrentHashMap<>();

Mono<InterfaceSnapshotResp> fetchMono = inFlight.computeIfAbsent(cacheKey,
    k -> permissionClient.interfaceSnapshot(...)
        .doFinally(signal -> inFlight.remove(k))
        .cache());  // Reactor cache() 确保多个订阅者共享同一结果
```

- 同 key 并发请求共享同一 `Mono`，只有首个触发远端调用
- `doFinally` 确保完成后清理（无论成功/失败）
- 不使用 Caffeine `AsyncLoadingCache`（与当前手动 `put`/`invalidate` 逻辑冲突，迁移成本高）

| 组件 | 改动 |
