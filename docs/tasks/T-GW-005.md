## 设计摘要

### 1. 失效标记

Gateway 本地快照有两种失效方式：

| 方式 | 触发 | stale-allow 可续命？ | 语义 |
|---|---|---|---|
| 自然过期 | Caffeine `expireAfterWrite` TTL 到期 | ✅ 可以 | 快照陈旧但未被主动撤销 |
| 显式失效 | 收到 `perm:invalidate` Redis 广播 | ❌ 不可以 | 权限中心明确告知权限已变更 |

**核心原则：权限主动撤销 > 服务不可达兜底。**

#### 标记维度

与当前 `InterfaceSnapshotCacheInvalidator.evict()` 驱逐维度保持一致：

| 事件载荷 | 标记/驱逐范围 | 说明 |
|---|---|---|
| `serviceCodes` 非空 | tenantId + serviceCode 下所有用户快照 | API mapping / 资源 / 条件规则变更 |
| `userIds` 非空 | tenantId + userId 下所有服务快照 | 用户角色关系变化 |
| 仅 `roleIds` 非空 | tenantId 级（所有用户快照） | Gateway 无法反查角色→用户，安全过驱 |

#### 标记数据结构

独立标记集合 `Set<String> invalidatedKeys`，与主缓存 `interfaceSnapshotCache` 并列：

```
interfaceSnapshotCache: Cache<String, InterfaceSnapshotResp>   // 主缓存
invalidatedKeys: Set<String>                                    // 显式失效标记集合
```

**选择理由**：

- 主缓存值类型不变，无侵入
- O(1) 查询性能（HashSet）
- 标记与缓存生命周期解耦，可独立清理

#### 标记操作

| 触发场景 | 操作 | 说明 |
|---|---|---|
| `perm:invalidate` 事件 | `invalidatedKeys.add(key)` + `interfaceSnapshotCache.invalidate(key)` | 标记 + 驱逐 |
| 回源拉取新快照成功 | `invalidatedKeys.remove(key)` | 新快照覆盖旧标记 |
| stale-allow 续命检查 | `invalidatedKeys.contains(key)` | 命中 → 不续命；未命中 → 可续命 |
| 缓存条目被 Caffeine 淘汰 | 无操作 | 孤立 key 由定期清理处理 |

#### 标记生命周期

- **创建**：`perm:invalidate` 事件触发时写入
- **清除**：
  1. 回源拉取新快照成功时清除该 key 的标记
  2. 定期清理：每 `stale-grace-seconds × 2`（默认 60s）扫描，移除不在主缓存中的孤立 key
  3. 订阅重连全量清空时一并清除
- **上限保护**：标记集合 > 主缓存条目数 2 倍时，触发全量清理（仅保留主缓存中存在的 key 对应的标记）

### 2. 订阅恢复策略：重连即全量清空

Gateway 与 Redis 断线重连后执行：

1. **清空主缓存**：`interfaceSnapshotCache.invalidateAll()`
2. **清空失效标记**：`invalidatedKeys.clear()`
3. **后续请求按需回源**：首次请求触发 `PermissionClient.interfaceSnapshot()` 拉取新快照

**设计理由**：

- **安全优先**：断线期间错过的 `perm:invalidate` 事件无法追回（pub/sub 无持久化），全量清空确保不存在陈旧权限
- **实现最简**：一次 `invalidateAll()` 完成，无需 Redis Stream 或 offset 管理
- **惊群可控**：Caffeine 单条回源 + 请求自带并发控制（同一 key 并发请求只有首个触发回源，其余等待结果）；TTL 30s 兜底已默认接受同量级延迟

**重连检测**：`PermInvalidationSubscriber` 需增加重连回调：

- Reactive Redis `listenTo()` 的 `onError`/`onComplete` 触发时标记订阅断开
- 重连成功后（`subscribe` 重建）触发全量清空
- 清空操作需在主线程执行，避免并发安全问题

### 3. 与 T-GW-003 stale-allow 集成契约

T-GW-003 实现 stale-allow 时，需遵循本规范定义的标记语义：

1. **续命前检查**：从 stale store 取出陈旧快照前，先查 `invalidatedKeys.contains(key)` → 命中则不续命
2. **续命窗口**：`stale-grace-seconds`（默认 30s）内可续命，超出转 closed
3. **续命不写回**：续命使用的快照不写回主缓存（避免陈旧数据覆盖未来新快照）

### 4. T-PERM-008 代码落地映射表

| 组件 | 改动 |
|---|---|
| 新增 `InvalidationMarker` | 封装 `invalidatedKeys` 集合操作 + 定期清理 + 上限保护 |
| `InterfaceSnapshotCacheInvalidator` | `evict()` 增加调用 `invalidationMarker.mark(key)` |
| `PermissionFilter` | 回源成功后调用 `invalidationMarker.unmark(key)` |
| `PermInvalidationSubscriber` | 增加重连检测 + 全量清空逻辑（cache + marker） |
| `GatewayProperties` | 新增 `gateway.cache.l1.stale-grace-seconds`（T-GW-001 定义） |
