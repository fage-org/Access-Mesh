## 背景

外评 P2×2（均成立）：①用户页 `loadTable` try/finally 无 catch——403/500/断网时 loading 复位但旧数据静默残留、无提示（**全仓唯一无 catch 的列表页**，其余十页均已有 catch+message）；②请求代际控制不全——快速搜索 A→B 时慢 A 迟到覆盖 B 的结果（代际已有局部先例：permission-change-log reqSeq、biz-domain configReqSeq、service-interface MappingForm treeRequestSeq；授予页 matrixToken 世代守卫成熟）。用户拍板的修法方向（2026-09-19 计划立项）：把已解决的交互范式下沉为通用 composable，收敛既有分叉实现并扩散到缺口页。处置历程见 decision-registry 2026-09-19 行。

## 范围

- 新 composable（`src/utils/` 或 `src/hooks/`，按仓库现状落位）：封装分页列表加载的代际守卫 + 错误提示 + 状态位 + 错误文案来源。
- 用户页试点接线，其余十页 hook 机械顺扫（同款模式复制，不逐页重构差异面；已有代际先例页收敛到统一实现）。
- 搜索/翻页/重置触发路径全部经代际守卫（onSearch/onReset/onPageChange 共用 loadTable 入口）。

## 当前口径

- 失败时保留旧数据 + 明确提示（比清空友好）；空态与错误态区分（空态=请求成功 items 为空）。
- 代际守卫用请求序号（latest-wins），不引入 AbortController（axios 取消语义对本场景非必需，序号更简单可测）。
- 锁分类纪律：仅对「新增行为」要求 old-fail；既有行为确认用特征锁，防止计划归档条件被假 old-fail 稀释。

## 验收对照

见 frontmatter acceptance。

## 非目标 / 遗留

- 表格级 stale 提示条（「数据可能过期」UI）——若本批未做，登记注记不阻塞。
- 非分页树形加载（role loadTree、org 树）——错误处理已较完整（try/catch+message），代际守卫执行期评估是否顺扫，不强求。
