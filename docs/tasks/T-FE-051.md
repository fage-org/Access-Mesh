## 背景

外评 P2×2（均成立）：①用户页 `loadTable` try/finally 无 catch——403/500/断网时 loading 复位但旧数据静默残留、无提示（**全仓唯一无 catch 的列表页**，其余十页均已有 catch+message）；②请求代际控制不全——快速搜索 A→B 时慢 A 迟到覆盖 B 的结果（代际已有局部先例：permission-change-log reqSeq、biz-domain configReqSeq、service-interface MappingForm treeRequestSeq；授予页 matrixToken 世代守卫成熟）。用户拍板的修法方向（2026-09-19 计划立项）：把已解决的交互范式下沉为通用 composable，收敛既有分叉实现并扩散到缺口页。处置历程见 decision-registry 2026-09-19 行。

Q-017（user/index.vue 死解构 + 点组织双请求）收敛载体=本卡（2026-09-19 拍板——T-FE-050 开工时裁定不顺带，两设想方向正是本卡 composable 化的设计决策面；定案见 decision-registry 同日行，Q 全文见 pending-problems）。

## 范围

- 新 composable（`src/utils/` 或 `src/hooks/`，按仓库现状落位）：封装分页列表加载的代际守卫 + 错误提示 + 状态位 + 错误文案来源。
- 用户页试点接线，其余十页 hook 机械顺扫（同款模式复制，不逐页重构差异面；已有代际先例页收敛到统一实现）。
- 搜索/翻页/重置触发路径全部经代际守卫（onSearch/onReset/onPageChange 共用 loadTable 入口）。

## 当前口径

- 失败时保留旧数据 + 明确提示（比清空友好）；空态与错误态区分（空态=请求成功 items 为空）。
- 代际守卫用请求序号（latest-wins），不引入 AbortController（axios 取消语义对本场景非必需，序号更简单可测）。
- 锁分类纪律：仅对「新增行为」要求 old-fail；既有行为确认用特征锁，防止计划归档条件被假 old-fail 稀释。

## 执行记录

### 落位与形态（按仓库现状定）

- **落位 `src/utils/list-load.ts`**（无 `src/hooks/` 目录；`src/utils/` 已有 spec 同置先例 tree.ts/wall-clock.ts）。
- **两层**：`useListLoad<T>`（通用列表——latest-wins 代际〔迟到成功/迟到失败均丢弃，`onLoaded` 副作用仅最新触发〕+ 失败 message〔`toErrorMessage` 后端 body 文案优先〕+ 失败保留旧数据 + `error` 标记〔四态：loading/error/空/数据〕+ loading 仅最新复位；`load()` 返回 boolean 供包装层级联判定）+ `usePagedList<T>`（叠 pagination/onSearch/翻页回调，total 仅随最新成功回写）。权限门禁/清空守卫留在各页包装层（不进 composable）。
- **错误文案统一 `src/api/_envelope.ts#toErrorMessage(e, fallback)`**：非 2xx（axios 形态）优先 `response.data.message`（R 信封），无 body 文案回落 fallback（不透出 axios 默认「Request failed with status code xxx」）；RequestError/普通 Error 透 message；非 Error 值 fallback。**service-interface 页局部 `getErrorMessage` 副本退役删除**（`e.message ||` 直透形态全顺扫面清扫替换）。
