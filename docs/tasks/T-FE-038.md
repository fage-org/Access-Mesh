# T-FE-038 权限授予页单类型矩阵上下文

> 状态：done（2026-08-07 实现完成；mock 先行，T-PERM-040 非前置；联调任务 T-FE-018 同时依赖 T-FE-038 + T-PERM-040 成为真正汇合点）
> 依赖：T-FE-036（v3 页面基线，review 中）；**mock 先行，T-PERM-040 非前置**（与 T-FE-036/T-PERM-034 先例一致，联调任务 T-FE-018 同时依赖 T-FE-038 + T-PERM-040 成为真正汇合点，2026-08-05 评审方案 B）
> 前置验收：见 acceptance（需求 9 项 + 加载体验）

## 背景

v3 权限授予页（T-FE-036）矩阵以"各资源类型混合"呈现操作列。单类型矩阵上下文定稿：矩阵一次只呈现一个 `resourceTypeCode`，资源树、操作列、角色主权限记录、ALL 虚拟行、操作继承计算、操作列显示配置全部绑定当前类型。本任务为前端增量改造。

## 范围

1. 中栏工具栏新增资源类型下拉（候选 = **资源类型定义全集**（type-definition/list），目标主体已有权限类型仅标记/排序、不决定候选全集，防首次授权死锁，§2.2），驱动 MatrixContext。
2. 操作列加载改为 `operation-permission/list` 携带 `resourceTypeCode + includeGlobalFallback=true`（后端合并，前端不再自行实现专属优先/全局回退领域规则；mock 阶段按 §3.2 语义模拟）。
3. 操作列隐藏配置改为 `permission-grant:hidden-columns:{resourceTypeCode}`（按类型隔离），并清理已不存在操作码。
4. 来源链计算（source-chain.ts）操作继承只消费当前类型最终生效定义。
5. 类型切换加载流程（§3.6）：未保存变更确认 → 清空 → 并行查询 → 构建 → 骨架屏 → 请求序号丢弃旧响应。
6. 列表/资源树查询按当前类型过滤；`apply-grant-plan` 提交保持唯一写入口不变（20008 错误码映射接入既有错误码表）。

## 完成记录

2026-08-07 实现完成（T-FE-036 基线增量改造）：

- **MatrixContext**：中栏工具栏资源类型下拉（候选 = `type-definition/list` 筛选 `type_key=resource_type` 全集，按 sortOrder 排序）；「已有权限类型」标记 = 主体切换时一次全量主权限查询，仅标记/排序（有权限的排前）；默认选中上次选择（`perm-grant:last-type:{subjectType}`）或候选第一个；候选为空 → 矩阵区 `el-empty`「暂无资源类型配置」；无主体时下拉禁用。
- **操作列**：`operation-permission/list` 携带 `resourceTypeCode + includeGlobalFallback=true`（后端合并语义由 mock 按 §3.2 模拟：专属优先、全局回退、binaryBit 升序；`null+true` = 仅全局）；切换类型必须重新查询（hook `loadMatrixForType`）；操作列隐藏配置键改 `permission-grant:hidden-columns:{resourceTypeCode}`（按类型读写），加载成功后清理不存在的操作码；原 subjectType 隔离键不再使用（§13.2 决策 7 修订）。
- **来源链**：`computeSourceChain` 输入（基线/树/操作）全部为当前类型数据，操作继承只消费当前类型最终生效定义（内部合并对已合并结果幂等，纯函数与 Golden fixtures 未改）；详情层保留全量资源树/操作只读依赖（子权限可跨类型，评审确认）。
- **类型切换加载流程（§3.6）**：确认放弃（取消中止）→ store `switchMatrixType` 立即清空 baseline/草稿 → 三类数据并行查询 → `matrixToken` 请求序号丢弃旧响应（A→B→C 最终 = C）→ 齐备构建 → 中栏 `el-skeleton` 骨架屏；失败不回滚（空态 + 可重试）；主体切换共用同一加载管线。
- **列表/资源树按类型过滤**：list `resourceTypeCode` 过滤主权限（子权限按 depend_on 挂父、跨类型不过滤，mock 按契约 §6.4 模拟）；`apply-grant-plan` 保持唯一写入口，mock 增加 20008 演练（creates 主权限 + children 嵌套校验 operationCode 适用性，与 20005 区分）。
- **行模型**：单类型矩阵 = ALL 虚拟行 + 当前类型资源实例树（无类型分组行）；实例树默认收起至第一层；无权限时矩阵始终渲染当前类型（评审确认，S11 首次授权不受阻），原「该主体暂无权限配置」空态被类型级空态取代（§3.1 修订）。
- **验证**：单测 105 全过（新增 switchMatrixType 5 场景）；`vue-tsc --noEmit` / `eslint` / `vite build` 全过；review 发现的候选为空路径标记缺失（should-fix）与 `kind:"type"` 死代码已修。

### 2026-08-07 实现评审三轮修复（review 2 问题）

1. **[P1] 三套代际未形成同一竞争域（已修）**：原 selectionToken（仅 handleSelectSubject 递增）与 matrixToken/baselineToken 各自为政，三个可复现缺口：① B 加载中点击当前主体 A（no-op）——A 只推进 selectionToken，B 的 store selectSubject 仍提交 context=B，树高亮 A 但保存作用于 B；② 空候选 A 标记在途时切分组——分组不推进任何代际，A 仍恢复并重新激活；③ B 加载中切类型 C——C 作废 B 的 baseline/matrix，但 B 的 !ok 分支仍把 currentTypeCode 回滚为旧类型。修复：**删除 selectionToken，matrixToken 升级为交互/加载统一代际**——主体选择（含 no-op）、分组切换入口统一递增并复位 matrixLoading（被作废请求的 finally 因 token 过期不再清理，防骨架屏卡死）；store 新增 `cancelPending()`（递增 baselineToken 作废在途 selectSubject/switchMatrixType 迟到响应 + 复位 baselineLoading，保留 context/baseline/changes，与 resetAll 区分）；handleSelectSubject 改为确认弹窗通过后才取得所有权（++代际 + cancelPending），补加载后以「恰好多一次加载（gen+1）」判定无新交互，主流程/回滚前校验同一代际。
2. **[P1] 并行失败仍提交新主体（已修）**：原 loadMatrixForType 的 Promise.all 中 selectSubject 与其他三类读请求并行，读请求先失败时 selectSubject 仍可能在途成功提交 context/baseline，页面树仍旧主体、保存却作用于新主体。修复：**先读后提交**——主体切换路径三类读请求（资源树/操作列/类型标记）并行，全部成功并校验代际后才调 selectSubject 统一提交（context+baseline 原子）；任一读失败整体失败、context 不提交（handleSelectSubject 回滚 currentTypeCode 并提示）；空候选路径同步改为「标记先读 → 成功后再 selectSubject 提交 → 提交成功才写标记」。
3. **验证**：新增单测 2 个（cancelPending 作废在途 selectSubject 不提交 context / cancelPending 不动已提交状态），单测 116 全过；`npm run typecheck` / `eslint --max-warnings 0` / `vite build` 全过。修复过程发现并修复派生缺陷：cancelPending 后被作废请求的 finally 不清理 baselineLoading/matrixLoading（页面冻结/骨架屏卡死），已同步复位。
4. **复查 should-fix（2026-08-07 晚，review 复核后补）**：① loadDeps 兜底原条件 `matrixToken === 0` 在统一代际后恒假（dead code）——候选晚于主体选择就绪时矩阵永不加载，改为「context 非空 + currentTypeCode 非空 + !matrixLoading + 资源树空」判定补加载；② 主体切换三读在途时类型下拉仍可达（原只拦 isSaving），类型分支读旧 context 加载导致"意图 B+C 得到 A+C"——`handleSwitchType` 增加 selectingKey/baselineLoading 检查拒绝并提示。

### 2026-08-07 实现评审四轮修复（review 5 问题）

1. **[P1] baselineLoading 阻断快速类型切换（已修）**：上轮 `handleSwitchType` 用 `selectingKey || baselineLoading` 判断"主体切换中"，但 baselineLoading 同时由 switchMatrixType 设置——类型 B 加载中选 C 被误拒停留在 B，违反 A→B→C 最终为 C 验收。修复：仅用 `selectingKey` 判断主体切换中（独立可靠），baselineLoading 不再参与类型切换保护。
2. **[P1] 旧主体请求清除新请求的选择状态（已修）**：A、B 快速连续选择时，过期的 A 流程 finally 无条件 `selectingKey = null`——B 仍在读阶段（baselineLoading=false）时保护被绕过，仍可"选择 B 得到旧主体 A + 新类型 C"。修复：`onSelectSubject` finally 按 key 值比较清理（`selectingKey === payload.key` 才清空），A 的迟到 finally 不清 B 的选择状态。
3. **[P1] 卸载未作废读阶段代际（已修）**：先读后提交流程在四类读请求期间卸载页面，resetAll 只作废已启动的 store 请求、matrixToken 未变——读请求卸载后仍通过 token 校验并 commitSubject 向全局 store 提交主体、继续路由后处理。修复：`onBeforeUnmount` 先 `++matrixToken` + 复位 matrixLoading + `cancelPending()` 再 `resetAll()`。
4. **[P2] 主体权限记录不再并行加载（已修）**：先读后提交把 selectSubject（含 fetchBaseline）串行化多一次网络往返，违反"资源树/操作权限/角色权限记录三类并行"验收。修复：store 拆分无副作用 `prepareBaseline`（预取主体权限记录，共享 baselineToken 守卫，过期返回 null，不设 baselineLoading）+ `commitSubject`（同步原子提交，saving 拒绝）；主体路径四类读取（树/操作/标记/基线）并行，全部成功并校验代际后 commitSubject；空候选路径同步「标记 + 基线并行预取 → commitSubject」。
5. **[P3] 验证证据再次回退为 114（已修）**：§13.4.1 验证行被挤到 §13.4.2 内容之后成为文档最后一条。修复：移回 §13.4.1 表格后并标注「首轮历史证据」，design 新增 §13.4.3 四轮修复表。
6. **验证**：新增单测 3 个（prepareBaseline+commitSubject 成功原子提交 / prepareBaseline 期间 cancelPending 返回 null / commitSubject saving 拒绝），单测 119 全过；`npm run typecheck` / `eslint --max-warnings 0` / `vite build` 全过。
