## 背景

外评 P1-04 + P3-14（同根因，均成立）。`refreshUserMenu()` 全仓仅 loginByUsername 与 initRouter 两处调用；权限授予页重试按钮（typePermDenied 降级态）读的仍是 store.permissions 旧值。场景：管理员给用户 A 新增 `USER:UPDATE` 后 A 的按钮不出现、撤权后按钮残留点击 403，只能 F5/重登。用户拍板（2026-09-19）：**403 触发自动刷新一次 + 手动入口**（弃轮询/推送——前者延迟=N 分钟且常驻请求量、后者需后端新事件机制属长期项）。

关键约束（外评修法盲点）：管理员授权发生在管理员自己的浏览器，页面内刷新帮不了被授权人——机制必须落在被授权人会话侧，403 触发正是「被授权人下一个动作即自愈」的形态。

## 范围

- 提炼统一「会话能力刷新入口」（单函数：权限串+侧栏+门禁 path 集/状态机原子更新），四个调用方共用：initRouter、403 自动刷新、手动入口、授予页重试——仅刷 store 不重建侧栏则「下一个动作自愈」只完成一半。处置历程见 decision-registry 2026-09-19 行。
- `src/utils/http/index.ts` 响应拦截器 403 分支（现仅注释「由页面层自行处理」）加自动刷新触发（去重窗口 + 不重放请求）。
- 顶栏「刷新权限」入口（lay-navbar 工具区）。
- `src/views/perm/grant/utils/hook.ts` `retryLoadDeps` 先走能力刷新入口。
- 回归锁：http 拦截器 spec + grant hook.spec 补用例。

## 当前口径

- 403 ≠ 必然权限变更（可能是配错/越权访问）——刷新无害（多一次 user-menu 请求），按钮显隐以最新事实为准。
- 刷新后 menus 变化不清理 multiTags 已缓存标签（标签指向的路由由后端 403 兜底）；此边界登记任务内注记。

## 非目标 / 遗留

- 服务端推送（版本号/SSE/WebSocket）——长期项。
- 403 自动重放原请求——不做（循环风险，用户重新点击即可）。
