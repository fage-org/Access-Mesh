# 决策提问协议（2026-09-06 定案，适用一切提问决策场景）

**规则**：凡要求用户做判断、选择、表态的输出，必须附带具体例子。只用抽象术语/机制名词描述问题即违规——用户会要求重讲，等于浪费一轮。

## 三要素（每个决策问题必含）

1. **场景**：谁想做什么——具体到页面/服务/主体/操作，走真实链路，不用内部代号。
2. **数据示例**：具体输入/JSON/表行/代码片段的形态，指到字段与值；素材取自代码、测试、日志，不编造。
3. **实际后果**：各选项的行为差异 + 「现在为什么没出事 / 出事时长什么样」。

反例（历史上被打回的写法）：「实例级授权两环节不真实」「ID 空间错位」。
正例形态：「sec 想只授权编辑 office-hours 一条条件 → 授权页选不到、配不进；后端拿 permission_condition.id 去 resource_entity.id 空间查 = 拿 A 系统编号查 B 系统档案；现在没出事是因为实际授权都是类型级先命中」。

## 形态升级

- 默认用三要素。用户仍看不懂 → **新手级结构**：先背景原理（配代码对比示例）→ 再分类对比表（哪类真会出问题/哪类触发不了）→ 选项只讲「这次顺手改多少」的行为差异（「把我当作新手」定规，不得假设前置知识）。
- 定案类存疑 → **场景走查**：主体 + 动作 + 后果一段话走完（如「服务注册→管理员停用→它的同步程序持密钥继续调同步接口照样成功 = 停用按钮管不住资源同步」）。
- **构造例子即自校验**：例子编不出来，或编出的场景在代码里不存在 → 说明提问方自己理解有误，先回炉再问（实证：举例对象在代码中不存在 → 该评审条目整条撤回）。

## 节奏与信号

- 讨论型一次只推进一条（核实 + 举例 + 方案），等用户表态再进下一条；AskUserQuestion 批量仅限攒齐一组对等决策项的场景。
- 用户以反问或自有方案回应 = **推翻原定案的信号**，不是请求确认：先核实仓库事实，把不相容的硬场景举例摆给用户要答案，答案齐了才算定案。
- 属实且修法唯一、最小、无设计取舍的事实性修正不必提问，直接修复并在汇报中说明——把「都交用户」做成过度决策同样违规。

历史触发实录存于会话记忆（explain-problems-with-concrete-examples），本文件只保留规则本体。
